# AGENTS.md

This file is the canonical, harness-agnostic guide for AI coding agents working in this repository — read by Claude Code, Codex, Cursor, and other coding harnesses. (`CLAUDE.md` points here.)

## Working Style

Behavioral guidelines to reduce common LLM coding mistakes. Merge with project-specific instructions as needed.

**Tradeoff:** These guidelines bias toward caution over speed. For trivial tasks, use judgment.

### 1. Think Before Coding

**Don't assume. Don't hide confusion. Surface tradeoffs.**

Before implementing:
- State your assumptions explicitly. If uncertain, ask.
- If multiple interpretations exist, present them - don't pick silently.
- If a simpler approach exists, say so. Push back when warranted.
- If something is unclear, stop. Name what's confusing. Ask.

### 2. Simplicity First

**Minimum code that solves the problem. Nothing speculative.**

- No features beyond what was asked.
- No abstractions for single-use code.
- No "flexibility" or "configurability" that wasn't requested.
- No error handling for impossible scenarios.
- If you write 200 lines and it could be 50, rewrite it.

Ask yourself: "Would a senior engineer say this is overcomplicated?" If yes, simplify.

### 3. Surgical Changes

**Touch only what you must. Clean up only your own mess.**

When editing existing code:
- Don't "improve" adjacent code, comments, or formatting.
- Don't refactor things that aren't broken.
- Match existing style, even if you'd do it differently.
- If you notice unrelated dead code, mention it - don't delete it.

When your changes create orphans:
- Remove imports/variables/functions that YOUR changes made unused.
- Don't remove pre-existing dead code unless asked.

The test: Every changed line should trace directly to the user's request.

### 4. Goal-Driven Execution

**Define success criteria. Loop until verified.**

Transform tasks into verifiable goals:
- "Add validation" → "Write tests for invalid inputs, then make them pass"
- "Fix the bug" → "Write a test that reproduces it, then make it pass"
- "Refactor X" → "Ensure tests pass before and after"

For multi-step tasks, state a brief plan:
```
1. [Step] → verify: [check]
2. [Step] → verify: [check]
3. [Step] → verify: [check]
```

Strong success criteria let you loop independently. Weak criteria ("make it work") require constant clarification.

**These guidelines are working if:** fewer unnecessary changes in diffs, fewer rewrites due to overcomplication, and clarifying questions come before implementation rather than after mistakes.

## Public Repository

Every tracked file is published on the public GitHub mirror (`tsukhani/play1`), `.claude/commands/` and this file included, and so is every commit message; both stay readable in the history after a later commit changes them. Never write the local environment into either, nor into a PR description or release notes: no address or name of a real machine (IPs, hostnames, internal domains), no SSH users, CI host or instance names, job names or service accounts, no names of the applications built on the fork or of their tickets, and no path the fork is installed at on a machine. Write "an application", "the CI host", "a nightly job" or "this checkout" instead. Fixtures and examples use `localhost`, `127.0.0.1` and reserved names such as `example.com`. `/public-check` searches what the next `/deploy` will publish, every commit since the last release tag, its added lines and its message, and the uncommitted changes, for all of these; the names it cannot derive from the machine live in the gitignored `.claude/public-terms.local.txt`, and `/deploy` runs it before anything else, and again with `zip` on the release zip it builds, for what the build generated.

## Project Overview

Play Framework 1 — a Java web framework (v1.13.x, requires Java 25+). The framework source is Java built by Apache Ant + Ivy. End-user applications consume the framework through a Gradle plugin (`framework/gradle-plugin/`) and a thin shell wrapper (the repo-root `play` script) that translates 1.12-era CLI ergonomics to Gradle.

## Build & Test Commands

The framework's own build still uses Ant. End-user apps use Gradle (see `Consumer build` below).

All Ant commands run from `framework/`:

```bash
cd framework

# Build
ant jar                          # Clean, compile, and create play-*.jar
ant compile                      # Compile only (no clean)

# Tests
ant unittest                     # Framework JUnit tests only (fast inner loop)
ant integration-test             # Real-Netty integration tests (test-src/integration/)
ant test                         # Full verification: clean + jar + audit-deps + unittest + integration-test + gradle-plugin-test
ant gradle-plugin-test           # The gradle-plugin's TestKit suite alone (shells out to :gradle-plugin:test)
ant test-single -Dtestclass=play.mvc.RouterTest  # Single test class (no package prefix in path, use dots)
ant test-single -Dtestclass=integration.SseFunctionalTest  # One integration class: builds the modules, runs on the integration classpath with integration-test's JVM arguments (PF-246)
ant compile-tests                # Compile tests + copy fixture resources, no run

# Other
ant javadoc                      # Generate API docs
ant package                      # Create distribution ZIP
ant resolve                      # Resolve framework/dependencies.yml via Ivy and update framework/lib/ in place. Run after editing dependencies.yml. Idempotent. -Dprune=true to delete stray jars; -Dverbose for Ivy detail (PF-62)
ant audit-deps                   # Fail on a jar in framework/lib/ that nothing reaches and dependencies-audit.conf doesn't justify. -Daudit.strict=false to report without failing
ant audit-census                 # Runtime half of the audit: drives the suites under -Xlog:class+load and reports which framework/lib/ jars actually supplied a loaded class. Opt-in, never fails the build
ant dependency-check             # OWASP dependency-check over every jar the release zip ships; fails at CVSS 7.0 after framework/dependency-check-suppressions.xml. Refreshes the NVD data once a day old (NVD_API_KEY speeds that up); -Dnvd.update=false scans what is there (PF-195)
```

`ant dependency-check` runs the separate Gradle build in `framework/dependency-check/`. It is a build of its own because a plugin on the root build would be resolved by every `play new` from a distribution. Its scan set has to name every directory `ant artifact` copies jars from: a new one there needs a line in `build.gradle.kts`. It also scans the gradle-plugin jar that `package` publishes, as `:gradle-plugin:jar` builds it (byte-identical to the published one), which the target runs first. The analyze task is forced never to be up to date, because its check covers neither the scanned directories' contents nor the NVD data, and it used to pass without scanning. It shares `~/.gradle/dependency-check-data` with the applications' scans, so its plugin version stays in step with theirs: `renovate.json5` disables updates to it, and a bump is made by hand together with the applications, one of whose nightly Jenkins jobs writes the database. The scan is not part of `test`, because CI has no NVD data. `/deploy` runs it before publishing and `/renovate` after a resolve. The zip ships `framework/dependency-check-suppressions.xml` for applications that scan `framework/lib` (documented in `dependency.textile`), so every suppression there must be true wherever the framework is installed:
- match the jar by `filePath`, written with `[/\\]` separators so it also matches on Windows; a jar scanned from a directory has a package URL only if it embeds its own Maven metadata, and many do not;
- suppress by CVE where the product match is right but the CVE is not, and by CPE only where the product is wrong;
- give the reason in `<notes>`.

The Gradle plugin lives at `framework/gradle-plugin/` and is built via `./gradlew :gradle-plugin:build` from the repo root.
Its own tests are gated by `ant test` via the `gradle-plugin-test` target (PF-171) — see Testing Patterns.

### Benchmarks against Helidon

`benchmarks/helidon/` (PF-236) measures the fork against Helidon 4.5.7 SE and MP, and against Quarkus 3.40.1 (PF-252):
- **The applications:** four minimal applications with the same endpoints (plain text, JSON, JDBC, JPA and SSE), each
  built by Gradle with the checkout's own wrapper, Quarkus with its own Gradle plugin, in JVM mode. They send the same
  security headers, the fork's defaults, which the Helidon applications add in a filter (PF-249) and Quarkus in its
  configuration; the README lists them and what else each sends. Keep them the same when the fork's defaults change.
- **The driver:** `run.py --framework <a built checkout>`. It measures startup with and without each one's AOT cache,
  load with oha, memory, and the edit loop under Gradle.
- **The load cells (PF-247):** HTTP/1.1 without TLS, kept-alive and with a new connection per request (what an
  application behind a proxy gets), HTTP/1.1 over TLS, and HTTP/2 over TLS at 1, 4 and 16 requests in flight per
  connection (what a browser served directly gets). The fork has no cleartext HTTP/2. The TLS cells use a self-signed
  certificate that `run.py` makes under its output directory at run time; never commit one. Before each TLS cell curl
  and oha must show the protocol, and h2load measures the HTTP/2 cells at 4 and 16 in flight again, since oha's own
  client is the limit there.
- **Helidon at its best:** `--helidon-writes` sets Helidon's `write-queue-length`, `smart-async-writes` and
  `TCP_NODELAY`. Helidon leaves `TCP_NODELAY` off, and on Linux the delayed ACK then holds every HTTP/2 stream and SSE
  event for 40 ms. With it on, Helidon's HTTP/2 is faster at 1 in flight and three (MP) to five (SE) times slower at
  16 on the laptop. Compare against the better setting per cell.
- **Quarkus at its best:** `--quarkus-threads worker|virtual` picks Quarkus REST's worker pool or a virtual thread per
  request (both built by the build step), and `--quarkus-tls boringssl|jdk` its TLS engine: by default the fork's own
  BoringSSL (`netty-tcnative-boringssl-static`, `quarkus.tls.ssl-engine=openssl`), which the load step proves loaded.
  Compare against the better setting per cell. Quarkus's own Gradle AOT build trains a cache the JVM refuses, on
  3.40.1 and 4.0.1, so the harness trains its `aot-jar` build itself; the README says why. It is 3.40.1 because 4.0.1
  deadlocks an event loop under HTTP/2 (quarkusio/quarkus#57911, fixed for 4.1): re-run on 4.1 once it is released.
- **Linux:** it runs there too. `--server-cpus` and `--client-cpus` pin with taskset, and `--guard-cpus` measures what
  other users' programs used of the benchmark CPUs and measures again above half a core. The README says how to keep
  Gradle out of the home directory and which h2load prints p99.
- **The output:** a JSON file per run and a summary table to quote on a ticket.
- **The target:** ADR 0003 keeps the fork on condition that it reaches Helidon MP's figures. PF-235's tasks are
  measured with this harness, before and after, in one session on one machine.
- **Not part of the build:** it takes about 40 minutes per application (a third of that with `--protocols h1`) and its
  figures depend on the machine, so `ant test` does not run it. It is excluded from the release zip (`benchmarks/**`
  in `build.xml`).
- **Idle memory:** the fork's idle RSS stays about 10 MB above Helidon MP's with the JVM's default heap sizing on a 48 GB machine, and the cause is G1's sizing, not a retained object (PF-240). The fork's live heap after a full GC is within about 1 MB of MP's, and its RSS after one is below MP's. The heap is 8 MB regions there, G1 sizes it at the startup remarks from the survivor and old regions in use, and the fork's start holds four where MP's holds three, so G1 commits 112 MB of heap to MP's 80. Most of the difference in live heap at those remarks is the central directories of the larger classpath, which every jar keeps in the heap once a lookup has opened it, and a lookup that misses opens them all; dropping the 49 jars that supplied no class, 2.1 to 2.4 MB of live heap, still left 112 MB. So compare the live heap (`jcmd <pid> GC.run`, then `GC.heap_info`) as well as RSS before keeping a cut for its memory.
- **Peak memory under load:** how much heap G1 commits is decided in a cold JVM's first collections, and run.py's first load cell is kept-alive plain text on a just-started JVM. After PF-255 that cell's peak RSS was 1,426 MB against 946 before, yet JFR over the measured window showed the build after PF-255 allocating less per request (15.0 against 16.0 KB), with as many young collections and as long pauses, and with JFR running both builds committed the same 1,296 MB. So read a peak-RSS change against the committed heap and the allocation per request before calling it a regression.
- **Pitfalls it already handles:** its README lists them; MP's Hibernate logs two warnings per JPA request unless
  `SessionImpl` is silenced. Keep them handled when changing an application.

## Architecture

### Core Request Lifecycle

`play.server` receives HTTP → `Router` resolves URL to controller action → `ActionInvoker` invokes the static controller method → `Controller` base class provides thread-local `request`/`response`/`session`/`params` → template rendering via `GroovyTemplate`.

### Per-request work

Work that gives every request the same answer is done once (PF-237), and each shortcut answers exactly what the per-request code answered:
- **Response headers:** `PlayHandler` formats the Date header once a second. The session store, the flash scope and `ValidationPlugin` delete their cookie only in a response to a request that carried it, whatever `application.session.sendOnlyIfChanged` says (PF-249): the three deletions were 294 of a plain-text response's 647 bytes of headers. The session store also deletes when the action changed the session (`session.changed`, a logout's `clear()`), carried or not: a browser withholds a `SameSite` cookie from a cross-site POST, and a `Strict` one from any cross-site navigation, yet accepts a deletion in the response to a top-level navigation, so a single logout an identity provider posts would otherwise leave the session in place. Never make that deletion depend on the request's cookies alone. With `application.session.maxAge` set, which applications commonly have, `restore()` writes the expiry stamp into a fresh session for a request without the cookie; that stamp leaves the session unchanged (`changed = false` after it), or every such response would carry the deletion again. `COOKIE_EXPIRE` is read once, when `Scope` loads, and the unit tests share one JVM, so `SessionMaxAgeCookieTest` runs each case in a child JVM started with the setting. So a deletion is no per-response cost any more, and `addToResponse` encodes every cookie with Netty's `ServerCookieEncoder`; PF-237's per-second cache of empty cookies' headers was removed with it. Guarded by `ScopeCookieDeletionTest` and `RequestPathFunctionalTest`.
- **Action lookup:** `ActionInvoker.getActionMethod` keeps what it found for an action name, with the class loader it found it in, in PROD only and for at most 1,024 names. DEV looks every time, because classes change there.
- **Controller calls:** in PROD, `ActionInvoker.invoke(Method, ...)` calls a method through a method handle once a reflective call has reached it, so the Result every action throws is not wrapped in an InvocationTargetException whose stack trace is filled in. Only for a public method of a public class in the unnamed module, and only with arguments reflection would take without converting them; anything else goes through reflection, which also keeps a failing class initialiser failing as it did.
- **Routes:** a `Router.Route` whose path pattern is plain text (letters, digits and `/ - _ ~ %`) compares the request's path with it, and a route without a host skips its `.*` host pattern and checks the domain for the line feed and carriage return that jregex's dot refuses.
- **Request headers:** copied in one pass. A name that repeats, one that lowercases otherwise in the default locale than in the root locale, or headers of any class but Netty's plain `DefaultHttpHeaders` (`CombinedHttpHeaders` iterates a name's values joined) takes the lookup by name.
- **No JAMon monitor per request:** nothing has read them since `/@status` stopped printing them (PF-90), and `http_server_requests` times the requests. Jobs and templates keep theirs.
- **Not done where a request does not need it:** the remote-address and loopback patterns are compiled once; the four logging-context fields go into `ThreadContext` in one `putAll`, in the order the four puts gave them, since each `put` copies the map; an empty query string is not parsed, though its bytes are still taken in the request's encoding, so an unknown charset fails as before; the full response takes the headers built for it rather than a copy; and `ValidationPlugin` does not ask an action without parameters for their annotations.

- **Plugin hooks (PF-255):** the hooks every request calls (the invocation and action hooks, `routeRequest`, `onRequestRouting`, `rawInvocation`) go only to the enabled plugins whose class overrides them, from `PluginCollection.Hooks`, which is built again whenever `getEnabledPlugins()` returns another list. A new per-request hook belongs in that table too.
- **Security headers (PF-255):** `SecurityHeadersPolicy` holds the five static headers as `AsciiString`, validated once, and a response that sets none of them takes them in one copy, which Netty makes without validating again because both header sets come from the same `DefaultHttpHeadersFactory`.
- **`request_id` (PF-255):** a version 4 UUID from `ThreadLocalRandom` (`ActionInvoker.requestId`), not `UUID.randomUUID()`'s `SecureRandom`. It is unique but not unpredictable: nothing may use it as a secret (the user's choice, 2026-11-26).
- **An action's annotations (PF-255):** `ActionInvoker.actionAnnotations` lists an action's annotations and its controller class's once per action in PROD, unmodifiable, in a `ClassValue` of the controller class; DEV builds the list every time, since a class redefined in place may change its annotations.
- **Thread-locals (PF-255):** Play's 29 static thread-locals are `play.utils.PlayThreadLocal`, which keeps its value in a slot of one per-thread holder, so a request's new virtual thread puts one entry in its `ThreadLocalMap` for all of Play's state, where it used to build, grow and sweep a map of about fifteen. The fields keep their type, `ThreadLocal`, and its behaviour (`initialValue` once, `set(null)` a value, `remove` an unset). A new static thread-local of Play's should be a `PlayThreadLocal` too; one made per object should not, since each instance holds a slot for its lifetime.

Guarded by `ResponseHeadersPerSecondTest`, `ActionLookupCacheTest`, `ActionInvokeHandleTest`, `RouteMatchingTest`, `RequestHeadersTest`, `RemoteAddressTest`, `ValidationPluginActionTest`, `PluginHooksTest`, `SecurityHeadersPolicyTest`, `RequestIdTest`, `ActionAnnotationsTest`, `PlayThreadLocalTest` and `integration.RequestPathFunctionalTest`, which checks what a request through the real server is given.

PF-255's cuts, each measured alone on the Linux benchmark server (HTTP/1.1 plain text, 6 event loops, two alternated runs each), took the work off the loop, a request's virtual thread and the carriers' scheduling, from 9.2 to 7.6 µs, and the whole request from 29.2 to 26.2 µs of CPU, 309k to 333k req/s: the hooks 0.57 µs, the headers 0.48 µs off the loop and 0.6 µs off the loop's encoding, `request_id` 0.26, the annotations 0.07, the thread-locals 0.24. The JFR CPU-time profile's inclusive shares had promised about twice that; measure a cut before counting on what a profile says it costs.

These cuts took a plain-text request's server CPU from about 59 to 53 µs and its allocation from 27 to 12.5 KB, and left the Helidon benchmark's requests per second where they were: in three alternations on 14 cores, medians of 77k against 77k before them and Helidon MP's 88k. A request's CPU is not what limits that figure. A request crosses threads twice, from its event loop to its virtual thread and back for the write, where Helidon's connection thread does its own reads and writes, and the figure follows how often an event loop has to be woken and how long a request waits for its loop. With 4 event loops instead of Netty's default of twice the cores (28 loops), a quarter of the cores, which PF-240 made the default and PF-244 raised to half (below), the same code served 84k to 85k on all four endpoints at p99 0.90 ms against MP's 0.87 (JPA 0.91 against 0.96), at 41 µs of server CPU per request against MP's 44, and SSE did not drop. The gap to MP grows with the connections, about 3 µs at p50 with one, 11 µs with 16 and 31 µs with 64, which is that wait. So measure a further per-request cut with the harness before keeping it for its throughput.

### Closing a connection

A response after which the server closes the connection says `Connection: close` (PF-257, RFC 9112 section 9.6). That covers a request that asked for it, an HTTP/1.0 request, and the 500 pages, which close after every response. `PlayHandler.closesAfter` sets the header: call it on any new path that adds `ChannelFutureListener.CLOSE`, before the response is written. The 404 page keeps a kept-alive connection open, as an action's own `notFound()` does; before PF-257 it closed every connection, unannounced. HTTP/2 and HTTP/3 drop the header in their stream codecs, which list it as connection-specific.

A streamed body (an SSE stream, an `InputStream` or other `ChunkedInput` response) is framed by `PlayHandler.frameStream`: chunked on a kept-alive connection, close-delimited on one the server closes after, so neither `Transfer-Encoding` nor `Content-Length` and the body ends with the server's FIN (section 6.3). HTTP/1.0 must never get `Transfer-Encoding` (section 6.1), and the fork sent it chunked bodies until PF-257. With a chunked body on a closing connection, the client also had the whole response at the terminating chunk, which goes out in a write of its own, and hung up while the server's FIN was on its way. Both ends then kept a TIME_WAIT: in the Quarkus head-to-head (PF-252) a client opening a connection per request took over a TIME_WAIT port on two connects in three, at ten times the connect time, and that was the new-connection SSE cell's p99. `Connection: close` alone did not change it, since the client had asked for the close and closes after the body either way. A truncated close-delimited body looks complete to the client: the price, paid only by a client that asked for the close. The compressor that `HttpServerPipelineFactory.buildHttpContentCompressor` builds passes a close-delimited body uncompressed, because Netty's encoder frames a compressed body of unknown length chunked again. Guarded by `integration.ConnectionCloseTest` and `CloseDelimitedCompressionTest`.

### Framework Bootstrap

`Play.java` is the main entry point — initializes configuration, plugins, classloader, and routes. Two modes: `Play.Mode.DEV` (hot reload, error pages) and `Play.Mode.PROD`.

### Virtual Threads

This fork runs on virtual threads exclusively. Request invocation (`Invoker`) and background jobs (`JobsPlugin`) each dispatch through their own `play.utils.VirtualThreadScheduledExecutor`, which uses two platform threads only for timer dispatch and unbounded VTs for actual work. Mail dispatch (`Mail`) has a separate thread-per-task executor on `VirtualThreadFactory("mail")`, gated by a `play.mail.maxConcurrent` semaphore (default 32). Java 25's elimination of `synchronized`-pinning (JEP 491) makes the VT path strictly cheaper than platform threads under blocking I/O; the legacy `play.threads.virtual*` toggles are gone. `Play.java` emits a WARN at boot if any of those keys are still in `application.conf` so operators notice.

The HTTP and HTTPS worker event loops default to half the cores, rounded up and never fewer than 2 (PF-244; `Server.defaultWorkerThreads`), not Netty's twice the cores. PF-240 made it a quarter, measured on 14 cores that the load generator shared; on the Linux benchmark server, whose 12 server CPUs nothing else shares, a quarter (3 loops) kept the fork at 4 to 5 of them, and in two alternations 6 loops served 305k plain-text requests/s over HTTP/1.1 against 3 loops' 182k, at p99 0.43 ms against 0.72, and 432k against 272k over HTTP/2 at 16 in flight (h2load). The loops only decode, encode and write, since every action runs on a virtual thread. Each loop is a platform thread with its own magazines in Netty's adaptive allocator, whose direct chunks (128 KiB and up) Netty 4.2 mallocs through the FFM linker on Java 25, outside the JVM's native memory tracking, so `VM.native_memory` never shows them: read them in `vmmap` (or `pmap`) as malloc. In three alternations of the Helidon harness on 14 cores, the same build with 4 loops and with `play.netty.maxThreads=28` served medians of 84.9k to 85.1k requests/s against 76.6k to 77.8k on the four request endpoints, at p99 0.90 to 0.91 ms against 0.96 to 0.98, and 40.4k SSE streams/s against 36.3k, at p99 0.61 ms against 0.78; peak RSS was 557 to 631 MB against 590 to 682 (SSE 866 against 886), a loop with two connections being woken for nearly every write. The floor of 2 is measured too: with the JVM sized for 4 cores (`-XX:ActiveProcessorCount=4`, same machine, the harness's oha load) a lone loop ran at 98 to 100% of a core and served medians of 71.6k to 76.1k requests/s at p99 1.71 to 1.75 ms and 37.8k SSE streams/s at p99 0.77, where Netty's 8 loops served 81.4k to 82.0k at p99 0.92 to 0.93 and 40.1k at p99 0.59, and 2 loops 86.7k to 87.4k at p99 0.88 to 0.89 and 51.3k at p99 0.51, at 33 µs of process CPU per plain-text request against the 8 loops' 43 (one run each). Netty's `io.netty.allocator.numDirectArenas` and `numHeapArenas`, which cap arenas apart from the loops, size `PooledByteBufAllocator`, which Netty 4.2 no longer uses by default (`io.netty.allocator.type` is `adaptive`), so they do not apply; `pooled` held more malloc than `adaptive`. `play.netty.maxThreads` and Netty's `-Dio.netty.eventLoopThreads` still decide when set. Guarded by `WorkerThreadsTest`.

PF-255 measured the count again with its per-request cuts, against Quarkus 3.40.1, on the same 12 CPUs (two alternations each), and the plain-HTTP listener now defaults to two thirds of the cores, rounded up and never fewer than 2 (`Server.defaultHttpWorkerThreads`; 8 on 12), while HTTPS keeps half (the user's choice, 2026-11-26). Over HTTP/1.1, 8 loops served 10 to 19% more cheap requests than 6, 395k plain-text requests/s against 332k at p99 0.29 ms against 0.38, and on JDBC 316k against 288k at 0.62 ms against 0.43; an action doing real CPU work (200 rows to JSON) was served as by 6, 76.9k against 75.2k at 2.22 ms against 2.14. The cost came only over HTTP/2: with that action at 16 streams in flight per connection, 8 loops reached a p99 of 246 ms against 6 loops' 30, at the same 72k requests/s, loops and busy carriers time-sliced on the CPUs and every stream of a waiting loop stalled. Plain HTTP never carries HTTP/2 (there is no h2c), and it is what an application behind an HTTP/1.1 proxy receives, so it takes the larger count and HTTPS the safer one. On 4 CPUs (server and client each pinned to 4 with `taskset`), 3 loops against 2 served 30% more plain text (155.6k requests/s at p99 0.80 ms against 119.8k at 1.04) and 16% more JDBC (121.1k at 1.46 ms against 104.7k at 1.17), and the CPU-heavy action as well (26.5k against 25.9k) but at a p99 of 8.39 ms against 6.12: on a small machine the larger count costs a heavy action's tail some over HTTP/1.1 too. With both listeners under heavy load at once a server runs more loops than cores. The larger count costs connections that carry one request each, which a proxy without upstream keep-alive sends: in the regression check after PF-255 (three builds alternated, 12 CPUs), a request on a new connection cost the fork 82 to 83 µs of CPU with 8 loops against 73.6 with 6, and the client, saturated in that cell, 190 to 202 µs against 171 to 173, so it served 10 to 14% fewer; the TIME_WAIT split between the two ends was the same in all three builds, so PF-257 is not the cause. The default stays (the user's choice, 2026-11-27), and `deployment.textile`'s nginx example keeps its upstream connections alive. Capping the virtual-thread carriers (`-Djdk.virtualThreadScheduler.parallelism`) so that loops and carriers fit the CPUs cut the cheap cells' tails, at 16 in flight on JDBC from 5.4 to 4.5 ms at 6 loops and 6 carriers, but left CPUs idle as soon as actions did real work: the heavy action lost 10% of its throughput at 6 carriers and 28 to 30% at 4, with a p99 of 138 ms. So a carrier cap is no default, only a setting for an application whose actions are cheap (in `jvm.memory`), and a change of either count wants a measurement with a CPU-heavy action beside the cheap ones. Guarded by `WorkerThreadsTest`.

An HTTP/2 connection's streams flush together (PF-244): `Http2OrHttp1Negotiator` puts a `FlushConsolidationHandler` (256 flushes, consolidating when no read is in progress) between `SslHandler` and the HTTP/2 frame codec. Each stream writes its response from its own virtual thread, and every `writeAndFlush` used to reach `SslHandler` as a flush of its own: one TLS record and one socket write per response, where Helidon's Nagle, on by default, sends several streams' writes in one segment. The flushes that arrive in one turn of the event loop now leave as one, so the responses written meanwhile are wrapped together; a lone flush only moves to a task in the same turn, so nothing waits as under Nagle. It sits after `SslHandler` on purpose: at the head of the pipeline it would batch the socket writes but not the records. On the Linux benchmark server, with the loop count unchanged, it raised plain text over HTTP/2 from 137k to 189k requests/s at 4 in flight and from 151k to 272k at 16 (h2load, p99 3.3 to 2.1 ms and 7.9 to 5.0), 122k to 127k at 1 in flight, and left HTTP/1.1 where it was. HTTP/1.1 has no such handler, since its connection has one response in flight. Guarded by `Http2OrHttp1NegotiatorTest` (where it sits) and `integration.Http2FunctionalTest` (64 streams in flight on one connection, each answered).

### Chunked-write backpressure

`PlayHandler.LazyChunkedInput.writeChunk` parks a writing virtual thread while 8 MiB or more is queued for a client that is not reading, until the event loop has drained the queue under 4 MiB or the stream closes (PF-134). A write made on the event loop never parks, because that loop is what drains the queue. An interrupt has to throw out of the park (PF-204): `PlayHandler.writeChunk` rethrows it as `UnexpectedException`, `SseStream.tryWrite` closes the stream on any failed write, and that is the only way an application can give up on a stalled client. An application's event bus, for one, interrupts a listener still writing at its 3 s deadline. So never catch `InterruptedException` in the wait loop, and never move the park to `LockSupport.parkNanos`, which returns on an interrupt without throwing. Guarded by `play.server.BackpressureParkTest`, whose `SseStream` case goes through the real `PlayHandler.writeChunk`.

A stream's writes reach the socket in batches (PF-238). `LazyChunkedInput.readChunk` hands over everything queued when it is called, up to `MAX_DRAIN_BYTES` (16 KiB: one TLS record, and HTTP/2's default largest DATA frame), in one I/O buffer, pooled and direct under Netty's default allocator, so as one HTTP chunk and one socket write; a lone chunk is still wrapped without a copy, and one above the limit goes out alone. Not a pooled heap buffer: Netty's allocator then keeps heap chunks for every event loop that asks for one, which on plain HTTP nothing else does, and they held 67 MB more heap after a full GC under the benchmark's `/sse`. Off the event loop each `ChunkedWriteHandler.resumeTransfer` is a task on that loop, so `writeChunk` returns true, and `PlayHandler.writeChunk` resumes, only for the first chunk queued since the last `readChunk`: the `resumePending` flag, which a writer sets after its offer and `readChunk` clears before its poll. A chunk written on an idle stream therefore still asks for a resume and goes out at once, and a burst puts one task on the loop. Before it, each of the 200 events of the Helidon benchmark's `/sse` was a task on the loop, a `doFlush` and a gathering write of its own, and the fork ran at half of Helidon MP's rate; now a stream takes about eight tasks and six or seven socket writes (7.7 and 6.5, by JFR over 3,000 streams), and in three alternations the benchmark measured a median of 34.8k streams/s against MP's 3.05k, at p50 0.45 ms against 5.2 ms and p99 0.82 ms against 6.1 ms. Keep the clear before the poll and the set after the offer, or a chunk can be left queued with no resume coming; and keep `closeChunked`'s resume unconditional, or a close that lands after the pending drain's last read is never seen. A flag left set while the channel is not writable is harmless: `ChunkedWriteHandler` drains again when it becomes writable. Guarded by `play.server.LazyChunkedInputDrainTest` and `integration.SseWriteLatencyTest`, which checks that a burst arrives whole and in order over HTTP/1.1, HTTP/2 and HTTP/3, also to an HTTP/1.1 client that stops reading until the writer parks on the high watermark and to an HTTP/3 one that holds its reads until the stream's flow-control window runs out (both leave the flag set while the channel is not writable), and measures the time from a write on an idle stream to its arrival (`RESULT,sse-idle`). That case runs first and warms the idle path with 10,000 idle writes of its own before it measures, past C2's 5,000 calls: otherwise its figure is that of whatever the JVM ran before, and a burst that took one task per event, as one did before PF-238, had warmed the path, and the same code then read as slower after the change than before it. Per idle event both builds make the same calls (one task, one `doFlush`, two reads, one socket write), and in eight paired runs on one machine their medians, 127 to 318 µs, were within its noise of each other.

`SseStream.send` and `sendEvent` build a frame in one builder (PF-240): Gson writes the JSON into it, it starts at `FRAME_CAPACITY` (128 chars), the JSON is split into `data:` lines only when it holds a line break, which Gson's compact output never does but a type adapter's `jsonValue` can, and an all-ASCII frame is copied straight into its bytes (`utf8`). Before, Gson wrote a string of its own, which was split, copied into a 16-char builder that grew twice, made a string again and then bytes. The Helidon harness's event allocates 646 bytes where it allocated 922, its own `Map.of` included. Measured alone, `/sse` from a fresh JVM with 10 s of warm-up and 20 s measured, in three alternations: 44.7k to 45.8k streams/s against 30.9k to 36.0k, at p99 0.52 ms against 0.69 to 0.81, with the same peak RSS, 906 to 915 MB against 907 to 917. G1 grew the heap to 768 MB either way, so the cut bought streams, not memory. The frames are the same bytes, guarded by `SseStreamTest`.

### Structured logging

`application.log.format=json` swaps the bundled `log4j.properties` (PatternLayout) for `log4j-json.properties`, which routes the console appender through `JsonTemplateLayout` with the bundled ECS template (`classpath:EcsLayout.json`). Default is `text` (no behavior change). `ActionInvoker.invoke` pushes per-request fields (`request_id`, `http_method`, `http_path`, `client_ip`, `action_name`) into Log4j 2's `ThreadContext` and clears them in the finally block; ECS mode emits them as flat JSON keys, text mode ignores them unless the operator extends the pattern.

java.util.logging is bridged into log4j2 too (PF-175): `log4j-jul` ships in `framework/lib` (pinned to log4j-core's version — a mismatched pair fails at runtime), and every Play JVM sets `-Djava.util.logging.manager=org.apache.logging.log4j.jul.LogManager`. JUL reads that once, before first use, so it must be a JVM arg, and the argv is built in five places that must stay in sync: `registerPlayJvmTask`, `spawnPlay`, `PlayAutotestTask`, `configureTestTask` (Gradle's `test` task, PF-230) and `bundle-play.sh`. Each puts it *ahead* of the conf/command-line args so an app's own value wins (the JVM keeps the last `-D`). `registerPlayJvmTask` and `configureTestTask` set it as a `systemProperty`, not a `jvmArgs` `-D`: Gradle emits system properties before jvmArgs, so a `-D` there would beat an app's `systemProperty(...)`. Guarded by the gradle-plugin's `JulBridgeArgsTest` (resolved value per task) and the framework's `JulBridgeTest` (the jars actually bridge, logger names intact). `-Dlog4j2.shutdownHookEnabled=false` (PF-189) sits right after it at the same five places, with the same precedence and for the same reason (log4j reads it when the first context starts): see Shutdown order below. `BundleLauncherTest.appJvmFlags` takes the application's flags to start after it.

### Metrics registries

`MetricsPlugin` installs a new registry on every start and closes the old one, so a DEV reload leaves anything still bound to the old one reporting into a closed registry (PF-203). Which registry a meter goes on therefore depends on its owner. An owner that outlives a reload registers on `Metrics.durableRegistry()`, a JVM-lifetime composite that `Metrics.install` hands each new registry to. The HikariCP pool is one: `DBPlugin` keeps it when the database configuration is unchanged, and Hikari takes a pool's tracker only once, so it cannot be moved. An owner that a reload discards registers on `Metrics.registry()` when it is made. The caches are such owners (`Caches.stop()` drops them), and `CaffeineCacheProvider.create` binds each one; a durable meter would keep pointing at the discarded cache, and Micrometer would give a re-made cache of the same name that old meter. `MetricsPlugin.bindCacheMetrics` still binds the caches made before the plugin installed its registry. Only a cache that records stats goes through Micrometer's `CaffeineCacheMetrics`: for one that does not, that binder registers just `cache.size` and logs a WARN, once per cache at every start (PF-223), so the provider registers that gauge itself, the same name, tag and description. Guarded by `integration.MetricsReloadTest` (a real DEV reload, read through `/@metrics`), `MetricsTest` and `CaffeineCacheTest`.

### Shutdown order

At SIGTERM the JVM runs every shutdown hook at once, so anything that must happen in order happens inside the one hook `Play.start()` registers, `Play.shutdownHook`: the server drain (`Server.gracefulShutdown`), then `stop()` (the plugins' `onApplicationStop`), then `LogManager.shutdown()`, last, in a `finally`. Not in `stop()`, which a DEV reload also runs.

The drain first waits, at most `Server.BIND_WAIT_MS`, for `Server.<init>` to finish binding (PF-188). Netty serves the HTTP channel as soon as it is bound, and `aot-gen` sends its SIGTERM right after the first answered request, so before this the drain terminated the event loops of the HTTPS and HTTP/3 listeners still to come: a refused bind, and a cache trained without HTTP/3. The constructor counts the latch down in a `finally` and also in `fatal()`, just before `Play.fatalServerErrorOccurred()`, because that call exits the JVM from inside the constructor, and the exit runs the drain while the `finally` is never reached. A new fatal path in the constructor must therefore call `fatal()`, not `Play.fatalServerErrorOccurred()`. Every listener binds through `Server.bind`, which turns a refused bind into the `ChannelException` the constructor catches: Netty fails the bind with the OS's `java.net.BindException`, which `syncUninterruptibly()` rethrows as it is, so a port in use used to leave through `Server.main` ("Failed to start", exit 1) instead (guarded by `ServerShutdownDuringStartTest.aPortInUseEndsTheStartInTheFatalError`). The wait holds no monitor, because `registerForShutdown` needs `Server.class`. Guarded by `ServerShutdownDuringStartTest`, which uses the package-private `Server.beforeBind` hook to begin the drain before a bind, or to refuse one.

log4j's own shutdown hook, which the first log4j context registers whenever it finds no configuration that disables it (always in a bundle or a start from the AOT cache, which have no `conf/` on the classpath), stopped the appenders while `onApplicationStop` still logged (PF-189). The launchers turn it off. A JVM that ends before `Play.start()` has registered Play's hook (`play precompile`, a start that fails in `Play.init`, a DEV server stopped before its first request) has the `play-log4j-shutdown` hook that `Server.main` registers instead, which stops log4j only when `Play.shutdownHookEnabled()` is false at exit, because otherwise it would race Play's hook again. Guarded by `integration.ShutdownLoggingTest` (a real bundle launch, a start from a real AOT cache, and both early exits, with an appender that writes as it goes, one that buffers and one behind `Async`) and the argv pins in `JulBridgeArgsTest` and `BundleLauncherTest`.

H2's own shutdown hook (`org.h2.engine.OnExitDatabaseCloser`) closed every embedded database at SIGTERM while `stop()` was still running, so an `@OnApplicationStop` job that wrote reopened it: a second lock, a second AUTO_SERVER listener and a second compaction, or a `90121 Database is already closed` (PF-201). `DB_CLOSE_ON_EXIT=FALSE` is no way out, because H2 refuses it with `AUTO_SERVER=TRUE`. `play.db.H2ShutdownOrder` therefore takes that hook out of the JVM by reflection, but only while `Play.shutdownHookEnabled()`. `DBPlugin.onApplicationStart` does it on every start once an H2 datasource is up, and a keeper virtual thread does it again every second. H2 puts its hook back whenever a database it had closed completely opens again, and that happens at runtime too: a pool of one closes its connection at every `maxLifetime` rotation, 30 min by default, so a retry on starts alone would lapse in production. `Play.shutdownHook` then runs H2's closer after `stop()` and before `LogManager.shutdown()`:
- at most once, and never in `stop()`: a DEV reload runs `stop()` too, and the closer leaves H2 marked `terminated` for the rest of the JVM's life;
- and not when H2's hook was back at the SIGTERM, which the JVM then started with every other hook. Its thread is no longer `NEW`, H2 closes the databases itself, and the two never run together.

A fallback hook of the fork's own runs the closer when `stop()` has run `play.jobs.stop.timeout` + 3 s without Play's hook finishing, and returns as soon as Play's hook is done. Its clock starts when `stop()` begins, which `Play.shutdownHook` signals after the server drain (`H2ShutdownOrder.stopBegins()`), or once the drain has had `play.shutdown.drain.timeout` + 3 s. A clock started at the SIGTERM would close H2 under the stop jobs of a shutdown whose requests held the drain up (an action parked in `await`, or a WebSocket action waiting in `Http.Inbound.nextEvent()` for its next frame, does not count as in flight: PF-121, PF-205). With nothing in flight the fallback fires 33 s after the SIGTERM, inside the launchers' 35 s wait. If any of the reflection fails, H2's hook stays, which is the behaviour before PF-201, and one WARN names the cause. Guarded by `play.db.H2ShutdownOrderTest` (which also pins the two H2 members it uses, so an H2 bump that renames `INSTANCE` or `onShutdown()` fails there) and `integration.H2ShutdownTest` (real launches that watch the lock file: a stop job's write, an AUTO_SERVER client from another JVM holding the database, a refused bind, a hook that hangs, a request that holds the drain longer than `stop()`'s budget, and a DEV reload).

### Context propagation

Nothing ambient follows work to another thread on its own: all of Play's thread-locals are plain, and every request, job and forked task runs on a thread of its own. `play.utils.ContextPropagator` (PF-177) carries exactly two values, the Log4j `ThreadContext` map and `Lang`, through a registry of `ThreadLocalAccessor`s; applications add their own with `register`, which replaces by key. `wrap(Runnable|Callable)` captures on the calling thread; on the running thread it records what that thread holds, applies the snapshot, runs the task and puts the recorded values back. It restores, never clears, which is what makes nested wraps and sibling forks compose, and it restores even when an accessor throws.

Jobs: `Job.getJobCallingCallable` captures when `now()`, `in()` or `afterRequest()` is *called* (`JobsPlugin.afterInvocation` submits only after `ActionInvoker` has cleared the map). The snapshot reaches `Job.call()` through a private thread-local hand-off, not a field: one job instance can be started more than once, and applications override `call()`. `call()` applies it after `before()` (`preInit()` clears `Lang`), puts a per-run random-UUID `jobId` for every job, scheduled ones included, and restores the thread in its finally block, since synchronous start/stop jobs and inline `run()` calls execute on their caller's thread. A job run with `call()` or `run()` on a thread that already has an invocation open (`InvocationContext.current() != null`: inside an action, or inside another job) joins that invocation instead of opening a second one: only its body runs, under a `jobId`, with no plugin hook and no transaction filter of its own, and a failure is thrown to the caller. A second lifecycle on the same thread ran every plugin's `invocationFinally()` against the caller's state — connection, EntityManager, validation, and the after-request queue, whose loss was a 500 (guarded by `InlineJobFunctionalTest`).

Deliberately not carried: the request, the response, the `Scope` holders, `Validation`, the JPA EntityManager map and the JDBC connection. **Never add an accessor for request-scoped objects or JPA/JDBC state**: a job's transaction closes every EntityManager on its thread, so a propagated map would close the request's (guarded by `ContextPropagationFunctionalTest.jobStartedFromARequestGetsItsOwnEntityManager`). An accessor's `capture()` must have no side effect and also runs on the working thread, which is why the Lang accessor reads `Lang.peek()` and not `Lang.get()` (that one resolves and stores a language and may set a cookie). The Mail and `WSAsync` executors are not wrapped (left for PF-20). Guarded by `ContextPropagatorTest`, `JobContextPropagationTest` and the integration `ContextPropagationFunctionalTest`, whose `ContextController` and four `/context/*` routes are live for every integration test.

### Boot timings

Every application start logs one INFO line through the `play` logger (PF-178), for example `Started in 703 ms: jvm=63 conf=37 logging=151 modules=0 plugins=15 classes=2 templates=- routes=259 onApplicationStart=37 onApplicationStart.play.plugins.MetricsPlugin=35 afterApplicationStart=0 bind=74 other=63`. `play.utils.BootTimings` holds one start's figures. `Play`, `PluginCollection` and `Server` charge phases to it with one-line `BootTimings.time(Phase.X, ...)` marks at the *call sites*, never inside the timed method, so no phase runs inside another and `other` (the total minus the phases) cannot go negative; keep it that way when adding a phase. PROD: `Play.init` begins the timings and `Server.main` logs once, after the bind, with the JVM's uptime as the total. `Server.main` exits on any Throwable, so the line must never be able to throw: where the `java.management` module is missing, the total counts from `Play.init` and `jvm` prints `-`. DEV: every `Play.start()` begins and logs a start of its own, so the `Play.init` phases and `bind` print `-`. `play precompile` logs nothing. A phase that did not run prints `-`, not `0`; a plugin whose `onApplicationStart` rounds to 0 ms is left out. A precompiled boot reads a routes file without template syntax as it is (PF-239), as a boot that is not precompiled does, and renders its precompiled template only when `Router.hasTemplateSyntax` finds one of the openings `TemplateParser` knows, comments included; only then does `routes` include the first use of the template engine. Otherwise that first use comes with the first template the application renders, which the AOT training run's `GET /` still makes when it answers with an error page. `GroovyTemplate` registers `String.if` through the metaclass from Java, not by evaluating a script, so the first use compiles no Groovy. A precompiled boot must load no compiler class (`com.sun.tools.javac.*`, `ApplicationCompiler`) and must start on a runtime that lacks the `jdk.compiler` module: `ApplicationClasses.compiler()` creates the compiler on first use (guarded by `BootTimingsLineTest.precompiledProdBootNeverLoadsTheJavaCompiler` and `precompiledProdBootStartsOnARuntimeWithoutTheJavaCompiler`; the latter also shows that a start which compiles on such a runtime stops with "This Java runtime has no Java compiler"). Guarded by `BootTimingsTest` (arithmetic and wording) and `integration.BootTimingsLineTest`, which boots scratch applications in child JVMs because where the line is logged depends on the real entry point. Documented under "Startup time" in `documentation/manual/production.textile`. JPAPlugin names `play.db.jpa.LazyFormatMapper.Json` and `.Xml` as Hibernate's JSON and XML format mappers unless the configuration, a system property or `hibernate.properties` names one (PF-239): Hibernate made Jackson's `ObjectMapper` and `XmlMapper` while it booted, about 590 classes, for applications that map no JSON or XML attribute. The lazy mapper makes Hibernate's own default on first use, in Hibernate 7.4's order (OSON unless disabled, Jackson 2, Jackson 3, JSON-B; Jackson 2, Jackson 3, JAXB), so a Hibernate bump that changes the order must change `LazyFormatMapper.create` too; `LazyFormatMapperTest` fails when the two pick different classes. The Bean Validation factory JPAPlugin hands Hibernate is a `PendingValidatorFactory`, built on a daemon thread with the start's context class loader while Hibernate builds its metadata: Hibernate first calls it when it integrates Bean Validation at the end of the session factory's build. JPAPlugin waits for it after the build, so a factory that cannot be built still fails the start with its own exception (guarded by `PendingValidatorFactoryTest`). `Server.main` initializes the classes in `Server.PREINIT` on a daemon thread before `Play.init` (PF-239): the Netty classes of the bind and the first request, and jregex's `CharacterClass`, whose Unicode tables Router's first pattern used to build on the main thread, 12 to 14 ms with an AOT cache, which cannot hold jregex's Java 1.1 classes. The thread also opens and closes a selector and a server socket channel and allocates one direct buffer. Without an AOT cache the bind phase went from about 60 ms to 17. Its handlers are the Netty ones of the default `play.netty.pipeline` (`HttpServerPipelineFactory.DEFAULT_PIPELINE`) and no others: `HttpContentCompressor`'s initialization extracts and loads brotli4j's native library, which PF-173 keeps off a start that does not compress, and with an AOT cache the main thread's first `defineClass` did not return until that load had finished, up to 100 ms later. None of them may come to depend on Play's state or on a default the application may still change, such as the time zone, and `PreinitTest` fails when a library renames one, when a handler outside the default pipeline is named, and when the preinitializer loads brotli4j. Netty reads its own `io.netty.*` system properties in those initializers (`io.netty.allocator.type`, `io.netty.leakDetection.level`, `io.netty.eventLoopThreads` and the like), so it now reads them before `Play.init`: one that code of the application sets at start, in a plugin's `onLoad` for one, no longer takes effect, and it belongs on the command line or in `jvm.memory`. Build-time metadata generation (the Micronaut/Quarkus approach) was weighed with this line and deferred: class definition is about 5% of the largest application's start and the two class scans it could replace cost about 4 ms. The record and its re-evaluation triggers are in `docs/adr/0002-defer-build-time-metadata.md`; do not add a metadata generator without one of them.

### Declared configuration requirements

`play.ConfigRequirements` (PF-179) is a registry of configuration keys that are checked together when the application starts. `require(owner, key)` demands a value: present, not empty after trimming, no `${...}` left unresolved. `requireIn(owner, key, allowed...)` constrains a value to a set, ignoring letter case and surrounding whitespace, and passes when the key is absent or empty; an unresolved placeholder is reported as missing by both. Keys nobody declares keep the WARN-and-leave-the-placeholder behaviour that `EnvVarConfigTest` and `SecretLockdownTest` pin. `Play.readConfiguration()` calls `ConfigRequirements.reset()` just before the plugins' `onConfigurationRead()`, which is the only place a plugin should declare: configuration is read in `Play.init` and again in every `Play.start()`, so a declaration made anywhere else is gone by the time it is checked. `reset()` also declares the framework's own keys again (today `application.log.format`: `text` or `json`, and `play.test.transaction`: `ambient` or `none`); new framework declarations go there, and the code that reads such a key must compare the way the check does (`Logger.LoggerInit` trims the format for that reason). `Play.start()` calls `ConfigRequirements.check()` beside the `application.secret` value check and throws one `ConfigurationException` listing every violation: exit 1 through `Server.main` in PROD, the error page in DEV, checked again on every restart. The check is deliberately not part of the read, so `play precompile`, `bundle` and `dist`, which return from `Play.init` before `start()`, succeed without production variables. A declaration owned by a plugin class is skipped while no loaded plugin of that class is enabled, because `plugins.disable` is acted on at the end of the same broadcast in which the plugin declared. `application.session.sameSite` is deliberately not declared: any value other than `Lax`, `Strict` or `None` (matched without regard to case by both `Scope.applySameSite` and the cookie encoder in `PlayHandler`, guarded by `CookieSameSiteTest`) leaves the attribute off the cookie, and declaring the key would refuse configurations that start that way today. `${VAR:default}` splits at the first colon and is not the shell's `:-` form; the skeleton's `https.port=${https.port:-1}` relies on that to yield `-1`. Guarded by `ConfigRequirementsTest`.

### Module System

Built-in modules in `modules/`: `testrunner` and `docviewer`. Each has its own `build.xml`, `app/`, and `conf/` directories. Both are auto-loaded by the Gradle plugin — `testrunner` when running under `play.id=test`, `docviewer` in dev mode — so apps don't declare them. Third-party modules use `play1 { modules("name") }` in `build.gradle.kts`; the plugin extracts each declared module under `modules/<name>/` before launch.

### Testing Patterns

**Framework-internal tests** (run against the framework itself):
- Framework unit tests: `framework/test-src/play/**/*Test.java` (JUnit 5) — invoked by `ant unittest`
- Integration tests: `framework/test-src/integration/**/*Test.java` (JUnit 5) — bind a real Netty server, exercise HTTP/1.1, h2 ALPN, h3, the SSE pipeline, and PlayHandler error paths. Invoked by `ant integration-test`; one class with `ant test-single -Dtestclass=integration.<Class>`. Test-app fixture lives at `framework/test-src/integration/testapp/`.
- Module tests: each `modules/*/build.xml` has a `unittest` target run by the framework's `module-unittest` (itself invoked at the end of `ant unittest`). docviewer and testrunner implement it. A module's target only sees what that build compiles — for docviewer that is `src/` alone; testrunner's compiles `app/testrunner/` beside its tests (see the `/@tests.list` paragraph below).
- `play` shim tests: `framework/test-src/play/PlayShimTest.java` — drives the repo-root `play` script through ProcessBuilder, `@DisabledOnOs(WINDOWS)` since it is `#!/bin/sh`. Lives in the framework suite rather than beside `BundleLauncherTest` because the shim is a repo-root file `ant package` bundles, not a gradle-plugin resource; it resolves the script at `${user.dir}/../play`. Every case puts a **stub `gradle` on PATH** — the bug it guards (delegating to a system Gradle from a non-application directory, so the shim's own guidance never printed) only reproduces when a system Gradle exists to fall through to, so a suite relying on the host lacking one would pass against the broken shim.
- Gradle-plugin tests: `framework/gradle-plugin/src/test/kotlin/**/*Test.kt` (JUnit 5 + Gradle TestKit) — invoked by `ant gradle-plugin-test`, which `ant test` calls after the integration suite. That target passes `--rerun` after both of the suite's tasks, so `ant test` never passes on an up-to-date skip: the suite reads things Gradle does not track, such as the Node and pnpm on the PATH. A plain `./gradlew :gradle-plugin:test` still skips when its inputs are unchanged. The plugin is a separate Gradle build, so no ant sourceset reaches it; before PF-171 the suite ran only on a manual `./gradlew :gradle-plugin:build` and the plugin shipped untested by CI. Wired into `test` rather than `unittest` so the fast inner loop stays fast. `BundleLauncherTest` drives the `#!/usr/bin/env bash` bundle launcher through ProcessBuilder. On macOS/Linux it simulates the MSYS branch with stubbed `uname`/`cygpath`; on Windows it runs the script through Git Bash (`Git\bin\bash.exe`, the shell an installed bundle starts with there — not the `bash` on PATH, which is WSL's), so that leg exercises the real branch, and one test starts a real JVM through the launcher on every OS (PF-183). On CI a missing Git Bash fails the class rather than skipping it. Off Windows every case runs the launcher under the bash `-PlauncherBash` names, `/bin/bash` by default (PF-227): it puts a directory holding only that bash ahead of the PATH, so `./play` still starts through its #! line, and each of the plugin's test tasks logs the bash and its version. On Linux `/bin/bash` is bash 5, while a stock Mac starts a bundle under bash 3.2.57, so `framework/gradle-plugin/bash32/test.sh` runs the class again under a bash 3.2.57 built from GNU's tarball, in a Temurin 25 image on Ubuntu. It needs only Docker, and the CI job `launcher-bash32`, which the release build needs, runs it: a construct bash 3.2 lacks, such as `declare -A`, `mapfile` or `${x,,}`, fails there. The locale-collation case skips itself, with the reason, under a bash or libc that cannot show its bug (bash 5, or musl). `.gitattributes` pins `*.sh` to LF because a CRLF checkout of `bundle-play.sh` is a launcher bash rejects. The suite's classes run in parallel forks (PF-219; `maxParallelForks` on the plugin's `test` task), so a new test must stay isolated: its own `@TempDir`, free ports, nothing written outside them. A test that goes wrong under the forks' load is tagged `@Tag("timing")`, which takes it out of `test` and into `timingTest`, a serial task that `test` depends on, so it never runs beside the forks: a bound of milliseconds, and a configuration-cache case that a changed file must reconfigure (`GradleSyncTaskTest`, `NewerLibraryRequestTest`). Under heavy file churn the second of those builds sometimes reused the cache although the file had changed, with file system watching on or off. The stop wait, 35 s in `bundle-play.sh` (`stop_wait_seconds`) and in `Play1Plugin.kt` (`stopWaitSeconds`), takes `PLAY_TEST_STOP_WAIT_SECONDS` when it holds a positive whole number: a test hook only, so that the tests of a stop that gives up do not wait 35 s. It is no operator setting, since the H2 shutdown fallback is timed to fit inside the 35 s, and the two copies parse it alike (guarded by `StopWaitTest` and the parity case in `BundleLauncherTest`).

**Testing module `app/` code (PF-164).** A module's `app/` — controllers, helpers, `*Plugin` — is compiled at *runtime* by `ApplicationClassloader` when the module is mounted, so it is not part of any ant-compiled sourceset and no JUnit test can reference it. Cover it by mounting the module into the integration fixture instead: `testapp/modules/<name>` is a marker file containing a path (`../modules/docviewer`), which `Play.loadModules()` resolves. Two gotchas — `Play.addModule` puts the module's `app/` on `javaPath` but *not* its `lib/*.jar` on the classpath, so module jars need adding explicitly (see `classpath.integration` in `framework/build.xml`); and the integration suite boots one shared `Play` in a single JVM, so a mounted module's routes and plugin are live for every integration test. This matters for real bugs: PF-163 was an infinite redirect loop arising from the interaction of the enhancer's cross-action redirect, reverse routing, and `prependRoute` precedence — reproducible only in a booted app, never in a unit test.

**End-user app testing** (run by app developers against THEIR apps, not the framework):
- `play test myapp` — backed by the `playTest` Gradle task. Starts the app in test mode (foreground, `play.id=test`). Apps put their tests under `app/` annotated with `@RunWith(PlayJUnitRunner.class)`; visit `http://host:port/@tests` to invoke them via the testrunner module's web UI.
- `play autotest myapp` — backed by the `playAutotest` Gradle task. Headless: boots the app, runs FirePhoque against `/@tests`, exits with the test result. Used for CI of end-user apps. Auto-synthesizes an ephemeral `${PLAY_SECRET}` for hermetic runs when neither `certs/.env` nor the host env supplies one.
- `./gradlew test` — Gradle's own `test` task, on the JUnit Platform, in `play1 { testJvms }` JVMs (PF-230, below). `--tests <Class>` or `<Class.method>` runs one; an IDE's Gradle test runner goes through it. `check` and `build` run it too.

`play test` and `play autotest` depend on `modules/testrunner/lib/play-testrunner.jar` (built by the testrunner module) — `ant test` does not run them against a real application. `./gradlew test` needs no testrunner jar (`PlayJUnitExtension.init()` adds `test/` itself), and `ant test` does run it against a real application (`TestJvmsTest`).

`/@tests.list` puts each unit test on FirePhoque's parallel lane (`U:`) or its single-permit database lane (`D:`) with `testrunner.DatabaseUseClassifier`, an ASM walk of what the test's bytecode reaches through application classes, including every implementor of an interface it calls (PF-154). The controller makes one per list, which reads each class once and looks up each interface's implementors once (PF-217): a walk that did both again for every test, at every interface call, `java.util.List`'s included, took one application's autotest start 4 to 5 minutes (279 s for the list before, 0.9 s after, every one of its 882 tests on the same lane). The class lives in the module's `app/`, not in `play-testrunner.jar`, and the controller must import nothing from that jar: every test-mode start mounts `_testrunner` and `Play.start()` compiles it, but `playStart`, `playRestart` and the integration suite have no testrunner jar on their classpath. It needs only the framework and ASM, so the module's `unittest` target compiles it with `DatabaseUseClassifierTest`, which counts both lookups.

`/@tests` records a class's failure as a whole, not only its tests' (PF-241). `TestEngine.Listener` records any container, the class, a nested class or the engine, that finishes FAILED or ABORTED, as a result of its own named "<class> (the class's setup or teardown)", and a class skipped as a whole (`@Disabled`) as skipped; `TestEngine.run` adds a failed result when JUnit ran no test in the class. Before, only `isTest()` identifiers were recorded, so a `@BeforeAll` that threw, an `@AfterAll`, a static initialiser, an extension's `beforeAll` or a refused `@Nested` class left no failed result, and a class with no failed result counts as passed: an application's cache test whose `@BeforeAll` asserted a cache server the CI machine lacked passed without running. A nested class whose constructor Play's enhancer duplicated is refused by Jupiter ("must declare a single constructor"), and that is reported too. The source line is the class's own frame nearest the test, as before, now also looked for in the exception's causes, where a class initialiser's frames are. Guarded by `integration.TestClassFailureTest`, which runs each case through `/@tests` in a scratch test-mode application and fails with the listener of before.

`playAutotest`'s verdict (PF-206) needs FirePhoque to exit 0 *and* `test-result/result.passed`. The marker alone is written by whichever server answers `/@tests/end` on the port, and an application's run whose worktree shared its port with another printed "All tests passed" beside 13 classes that had gone ERROR. FirePhoque exits 1 when any class FAILED or went ERROR, and, given `-Dapplication.path`, which the task passes, it stops before `/@tests/init` when the results folder that `/@tests.list` names is not that application's `test-result`, so it never deletes another application's results or posts a verdict into its folder. That check is what makes FirePhoque's per-class polling, and with it the exit code, about this application's own result files, so the task keeps no class list of its own. `/@kill` still stops whatever DEV-mode server holds the port, by decision. Guarded by the gradle-plugin's `AutotestVerdictTest`, which compiles the real FirePhoque from `modules/testrunner/src` against its htmlunit jars and runs it through `playAutotest` against a scripted fake server; the plugin's test task declares those two directories as inputs.

`play.test.transaction` (PF-231) decides whether the code of a test class runs inside a JPA transaction it did not open. `ambient`, the default, is what `/@tests` has always done: `TestRunner.run` runs each class in a `Job`, `TestEngine.run` launches JUnit on that job's thread, and every test of the class shares the job's transaction, which commits only when the class ends. The request a `FunctionalTest` sends is an invocation of its own on `TestEngine.functionalTestsExecutor`, so it never sees what the test saved. `none` runs the class's code with none of the runner's transactions open. `play.test.TestTransaction` is the only place the key is read: `ambient()` compares it trimmed and without regard to letter case, as `ConfigRequirements` checks it. Under `none` the class's code runs through `JPA.OwnTransactions`. Each call sets the thread's JPA contexts aside and puts in their place the ones the class's earlier calls left open, so a transaction opened with `JPA.startTx` in `@BeforeEach` is still open in `@Test`, as in plain JUnit. One still open when the class ends is rolled back and closed, and `JPA.em()`'s failure inside says how to open one. Two places call it, and a runner honors the setting by running classes through either:
- `PlayJUnitExtension`, an `InvocationInterceptor` around the constructor and every method of a `BaseTest`, factory, template and dynamic tests included. It holds one `TestTransaction.ClassScope` per outermost class, kept in that class's JUnit store, which closes it when the class ends.
- `TestEngine.run`, whose `TestTransaction.run` around the launch covers a class that is no `BaseTest` and the plugins' runners.

Never wrap each method in a `JPA.withoutTransaction` of its own: it rolls back what the method leaves open, so a transaction opened in `@BeforeEach` never reached `@Test`. Under `ambient` both run the code as it is. A runner that is to give `ambient` its `/@tests` meaning must therefore hold a transaction around each class itself when `TestTransaction.ambient()` is true, as `TestRunner`'s `Job` does; the JUnit Platform runner below runs each class in a `TestClassJob` for that. A class that is no `BaseTest`, on a runner that does not go through `TestEngine.run`, is reached by neither and runs as that runner leaves it. Under `none`, `Fixtures` called with no transaction open opens and commits one of its own; under `ambient` it joins the caller's, as before. Under `/@tests`, an inline `job.call()` from a test joins the runner job's invocation (PF-177), so under `none` it has no transaction. The key is declared in `ConfigRequirements.reset()`. Guarded by `play.test.TestTransactionTest`, `play.db.jpa.JPAWithoutTransactionTest`, `play.TestTransactionRequirementTest` and `integration.TestBodyTransactionTest`. The last boots scratch test-mode applications in child JVMs on free ports, runs their classes through `/@tests`, and needs `modules/testrunner/lib/play-testrunner.jar`, which `ant modules` builds.

Gradle's `test` task runs an application's `test/` classes on the JUnit Platform (PF-230), in `play1 { testJvms }` JVMs, `-PtestJvms` winning, `DEFAULT_TEST_JVMS` (2) otherwise: `maxParallelForks`, with Gradle's own one class at a time per JVM. `configureTestTask` in `Play1Plugin.kt` wires it: `useJUnitPlatform()`, the test runtime classpath plus `playClasspathFor(includeTestrunner = true)`, the argv of the other Play JVMs (above), `-Dplay.test.startApplication=true`, `-ea` off, and `app/`, `test/` and `certs/.env` as inputs, since Play compiles the first two from source. An environment variable is no input, so a run that only changes one needs `--rerun` (the manual shows how an application names its own as inputs). The count is set in an `afterEvaluate`, because an eager `tasks.withType<Test> { }` above the `play1` block realizes the task, and with it the plugin's configure action, before the block has run. Gradle passes `-Xmx512m` to a test JVM whose task names no heap, after every other option, so the task names the heap `jvm.memory`'s flags give, as HotSpot sizes it: `testJvmMaxHeap` (the last `-Xmx` or `-XX:MaxHeapSize`, else `-XX:MaxRAMPercentage` of `-XX:MaxRAM` or of the memory, 25% of at most 128 GB without either; JDK 25 has no `-XX:MaxRAMFraction`). `TestJvmHeapTest` compares it with what this machine's JVM sizes for the same flags. `-Dplay.test.startApplication=true` turns on `play.test.PlayTestSession`, a `LauncherSessionListener` registered through `META-INF/services` in play's jar and inert without it, `/@tests`' own launches included. When the session opens, before Gradle loads a test class, it takes the lowest free number from 1 by a file lock in `tmp/test-jvms/` into the `play.test.jvm` system property (so `${play.test.jvm:0}` gives a `%test.` path per JVM), runs `PlayJUnitExtension.init()` (`Play.init`, `test/` on `javaPath`), starts `Server` with `--http.port=0` (and `--https.port=0` when `https.port` is set), then `Play.start()`, which is `Server.main`'s order, so `onApplicationStart` and `@OnApplicationStart` jobs see the bound port in `http.port`, and makes Play's loader the thread's context loader. Gradle 9 captures that loader right after opening the session and loads every test class through it (`JUnitPlatformTestDefinitionProcessor.createTestExecutor`), so the classes are the ones Play compiled and enhanced from `test/` and `app/`, never Gradle's `build/classes`: models loaded from there are unenhanced. Port 0 binds a port the system picks, which `Server` puts in `http.port` and in `Play.boundPorts`, which every configuration read puts back, so a DEV restart keeps it (guarded by `HttpPortArgumentTest`). With Play started by a JUnit Platform runner (`useCustomRunner`), `PlayJUnitExtension` runs each outermost class in a `TestClassJob`: a real `Job` started with `now()`, as `TestRunner.run` starts one, whose body runs the class's calls, `TestEngine.initTest` and every intercepted constructor and method, on the job's thread until the class's store closes. So the class has the invocation, the plugin hooks and filters, and under `ambient` the transaction `/@tests` gives it, committed after the class. JUnit's own thread hands each call over and waits, as Jupiter's `SEPARATE_THREAD` timeouts do. The interrupt status travels with the call as if it ran on JUnit's thread: an interrupt of the waiting thread, or the status it hands over with, reaches the code, the waiting thread leaves with the status the code left, and the job's thread is cleared after each call. JUnit 6 clears its own thread's status when a test ends, so a test that leaves it set does not reach the next one, as under `/@tests`; a status left on the job's thread ended the job at its next `take()` and failed every later test of the class. The status a call is handed over with is set on the call before it is queued (PF-254): handed over in the caller's wait, it reached a call the job's thread had already started whenever the caller was descheduled after the add, and a test reading the status its `@BeforeEach` left failed now and then (guarded by `TestClassJobTest`, which holds the caller there). Other extensions' callbacks, `@MethodSource` factories and `@EnabledIf` conditions stay on JUnit's thread (no `InvocationInterceptor` hook reaches them), and a class that is no `BaseTest` gets no job. The bytecode cache under `tmp/`, which the JVMs of a run read and write at once, is written beside its file and moved over it (`BytecodeCacheTest`). Guarded by `TestJvmsTest` (a real application on this checkout's framework, which `ant jar` builds: two JVMs with a static and a server each and a fixed `%test.http.port` held by the test, the port an `@OnApplicationStart` job saw, a leaked interrupt status, the class transaction, a failure's message and line in the XML and on the console, `--tests` for a class and a method, one method and one class through the Tooling API's `TestLauncher` as an IDE runs them, PF-231's `none` suite with `java.enablePreview`, and the JVM count's DSL and `-P` beside an eager `withType`, and the heap), `TestJvmHeapTest`, `JulBridgeArgsTest`, `DotEnvPrecedenceTest` and `OneCopyPerLibraryTest`. Every case among them that runs the test task is off on Windows, so the runner is unverified there, and IntelliJ IDEA itself has never been run against it: fix what users report, and do not describe either as verified. On a synthetic suite of 24 classes on 14 cores, `playAutotest`'s lanes took 14 to 16 s at 0.9 to 1.1 GB peak RSS (server JVM and FirePhoque), and the runner 15.5 s at 0.5 to 0.7 GB in one JVM, 9.5 to 9.7 s at 1.1 to 1.3 GB in two, 8.1 to 8.6 s at 1.9 to 2.5 GB in four and 9.3 to 16 s at 3.3 to 3.4 GB in eight. `playAutotest`, `/@tests` and `play test`'s page are unchanged.

### Consumer build (Gradle plugin + `play` shim)

End-user apps use Gradle. The Play 1 plugin is at `framework/gradle-plugin/src/main/kotlin/play/gradle/Play1Plugin.kt` and exposes a `play1` task group: `playRun`, `playStart`/`playStop`/`playRestart`, `playTest`, `playAutotest`, `playPrecompile`, `playAotGen`, `playBundle`, `playSecret`, `playEvolutions`, `playDist`, `playClasspath`, `playModulesInfo`, `playJavadoc`, `playStatus`, `playPid`, `playOut`, `playNewApp`, `playClean`, `playVersion`, `playFrontendSpa`.

The repo-root `play` shell script is a thin wrapper that:
- Locates `./gradlew` (CWD), then `$PLAY_HOME/gradlew` (when in framework dir), then system `gradle` on PATH.
- Translates 1.12-era flags to Gradle wire format: `--http.port=X` → `-PhttpPort=X`, `--%test` → `-PplayId=test`, `-Xmx...` etc. accumulate into `-PjvmArgs="..."`.
- `play new <name>` runs the framework's `gradlew playNewApp -Pname=<name> -Pdest=<absolute>`. `<name>` may be a path (PF-182): the app is created there and `-Pname` is its last segment.
- Removed commands (`play deps`, `play idealize`, `play install`, `play list-modules`, `play check`, etc.) print a redirect message and exit non-zero.
- Under Jenkins (`JENKINS_URL` set) or a CI that sets `CI` (anything but `false` or `0`), every Gradle run gets `--no-daemon` (PF-197), `play new` included. Builds that overlap on one CI user used to share daemons, and Jenkins kills the processes a build started when that build ends, so a daemon one job's build had started died under another job's build. `PLAY_GRADLE_DAEMON=true` keeps the daemon under CI, and `=false` drops it anywhere. `PlayShimTest` clears all three variables in its `run` helper, so a suite running on a CI server stays deterministic. On a Jenkins host, `org.gradle.daemon=false` in the build user's `~/.gradle/gradle.properties` also covers the jobs' direct `./gradlew` steps.

Module loading happens via the plugin's `extractPlayModules` task: each module declared in `play1 { modules(...) }` is sourced from the framework distribution and unzipped under the app's `modules/` directory. `Play.loadModules()` and `VirtualFile` are unchanged from 1.12 — modules remain real directories on disk so overlays and hot reload keep working.

Each library in `framework/lib` reaches an application once (PF-192). The plugin adds `framework/lib` as plain files, which Gradle cannot match to a module, so it used to resolve the application's own copy of the same library beside the fork's, and with the resolved jars first, that copy loaded. `ant jar` writes `framework/lib-coordinates.properties` (`play.deps.LibCoordinates`; gitignored like `play-*.jar`): `<jar>=<group>:<artifact>:<version>[:<classifier>]` per jar, empty for a jar without coordinates, which means the vendored `jj-*` jars and a `dependencies.yml` entry that names no group. Only `jregex` is written that way, because no Central artifact is that jar; give every new entry its group. The same step fails when a jar in `lib/` matches no entry or an entry has no jar, so a Renovate bump that has not been through `ant resolve` now fails CI. In `afterEvaluate` the plugin excludes each such module from `compileClasspath`, `runtimeClasspath`, `testCompileClasspath` and, since Gradle's `test` task runs with the Play classpath (PF-230), `testRuntimeClasspath`, and warns once per declaration of one, which is now inert. An application whose build locks its dependencies rewrites the lock for `testRuntimeClasspath` once, because the libraries it used to resolve there are gone from it. The exclude also drops whatever reached the application only through that module, which nothing reports: `framework/lib` holds what the fork itself uses (`transitiveDependencies: false`), so an application that needs more declares it (on one application only a `pom`-packaged `jackson-bom` went). A module in `play1 { appManagedLibraries(...) }` keeps the application's version instead: no exclude, and `frameworkLibFor` leaves the fork's jar off every classpath and out of `playBundle`. A framework without the file excludes nothing. Guarded by `OneCopyPerLibraryTest` and `LibCoordinatesTest`.

The excluded edges took with them the version a dependency asked for, so a dependency built against a newer copy ran on the fork's older one without a word (PF-194). `reportNewerRequests` resolves the graph of the same declarations without the excludes, metadata only, in a detached configuration carrying `runtimeClasspath`'s attributes, and warns once per module a dependency asks for above the `framework/lib` version or through a range that version is outside of. It skips constraint edges, the application's own declarations (those get the "has no effect" warning), modules in `appManagedLibraries`, and requests from a module the fork replaces or from anything reached only through one, since none of those reach the classpaths. A managed module's own requests are checked, because its jar does reach them. The comparison is `GradleVersionOrder`, a copy of Gradle's documented ordering, because Gradle exposes no public comparator. A failure to resolve that graph warns and never fails the build. `failOnNewerLibraryRequests` (DSL, or `-P`, which wins) turns the warnings into a `GradleException`, since Gradle drops WARN under `-q`. Guarded by `NewerLibraryRequestTest` (including a configuration-cache run) and `GradleVersionOrderTest`.

`play1 { importFrameworkBoms = true }` (PF-193, opt-in) adds `platform(<bom>:<version>)` on `implementation` for each family in `FRAMEWORK_BOMS`: an anchor module, whose `lib-coordinates.properties` version is the family's, and its BOM. It is not added for a family whose anchor the application manages. That table admits only BOMs that manage their own family alone, which keeps out `hibernate-platform` and `jaxb-bom`, and only anchors whose BOM is published with every release. When a Renovate bump or a removal changes an anchor, check that its BOM exists at the new version. `FrameworkBomsTest` checks that every anchor is still in the real `lib-coordinates.properties`.

`certs/.env` is loaded into the JVM's environment by whatever launches it, never by Play itself — in the same five places as the JUL arg: `registerPlayJvmTask`, `spawnPlay`, `PlayAutotestTask` and `configureTestTask` (through `loadDotEnv`), and `bundle-play.sh` (`load_dotenv`, a bash port of the same grammar). One rule everywhere (PF-184): a variable the host environment already defines wins, even when empty, and the file is literal `KEY=VALUE` text that is read, never sourced. `registerPlayJvmTask` and `configureTestTask` apply the file and the ephemeral secret in a `doFirst` (`applyLaunchEnvironment`), never while the build is configured: a task's `environment` is filled from the build's own when first read, and one changed during configuration has Gradle store the whole map in the configuration cache entry, so every build that reused the entry started the JVM with the host environment of the build that stored it (PF-230). Guarded by the gradle-plugin's `DotEnvPrecedenceTest` (the four plugin sites, and the two `doFirst` sites across builds that reuse one configuration cache entry) and `BundleLauncherTest` (the launcher).

The JVM flags an app declares in `application.conf` — `jvm.memory`, `javaagent.path`, `agentlib`, the `jmx.*` keys and `java.enablePreview` (PF-229, `--enable-preview`, last) — are implemented twice as well: `confJvmArgs` in `Play1Plugin.kt` for the four Gradle sites, and `conf_jvm_args` in `bundle-play.sh`, a bash port of it (PF-183; before it a bundle ignored them all). Both emit them after the JUL arg and before the command-line flags, so the command line wins. `BundleLauncherTest` runs the launcher and `confJvmArgs` over the same conf files and compares the output, so change the two together. `jmx.port` + `jmx.hostname` start an agent that demands a login and TLS; only a literal `jmx.authenticate=false` / `jmx.ssl=false` turns either off (the 1.12 launcher hard-coded both off, and the JDK reads any value but `true` as off, so the value is normalised rather than passed through). The files they need come from `jmx.password.file`, `jmx.access.file` and `jmx.ssl.config.file`. These are keys of their own because the agent's flags come after `jvm.memory` and the JVM keeps the last `-D`. `ConfJvmArgsTest` pins the Kotlin side, including that a blank conf value is unset rather than swallowing the next line. `conf_jvm_args` reads all its keys with one `conf_values` call, one awk pass over the file (PF-239), and `conf_value` is `conf_values` for a single key, so the two cannot read a key differently. The launcher's run and start pay for every process it starts, twelve awk where one does; a new per-start lookup belongs in that call, and a new per-start helper process wants a builtin instead (`.classpath` is joined by a read loop, `SCRIPT_DIR` cut by a parameter expansion; a `$0` with a backslash, a Windows path handed to Git Bash, still goes to `dirname`, which there cuts at `\` too, guarded by `BundleLauncherTest`'s case of the launcher started by whatever path). Keep `uname` a process: `BundleLauncherTest` stubs it to take the MSYS branch. A bundle passes no `-javaagent` of its own (PF-239): the framework jar's agent is `HotswapAgent`, which only a DEV-mode reload uses, and a bundle always runs precompiled, so PROD. The Gradle launch sites keep it, for `playRun`'s DEV reload.

### Compiling the application (javac)

`play.classloading.ApplicationCompiler` compiles the application's sources with the JDK's own javac through `javax.tools`, in the JVM that defines the classes, in DEV, test and precompile mode alike (PF-229). ECJ is gone from `framework/lib`. Before PF-229 Play defined ECJ's bytecode while the plugin's `compileJava`, where an application's compiler plugins run, compiled a sibling copy that nothing loaded. The sources are `ApplicationClass.javaSource`; the classes stay in memory and go to `ApplicationClass.compiled()`, inner, local and anonymous classes included. Its `FileManager` shows javac each application class once: as `javaByteCode` when Play has compiled it, otherwise as its source on a source path made of `Play.javaPath`, which javac then compiles too (`-implicit:class`). A class file on the JVM classpath (Gradle's `build/classes`) is left out of a listing when its top-level name has a source in that package of `Play.javaPath`, because javac would take the newer of the two. The check reads one listing of each package's directories per compile: a `getJava` per class file cost 19 ms of each compile in a package of 1,500 classes. The `Compiled` file objects are kept from compile to compile while a class's bytes stay the same. `FileManager.flush()` does nothing, because javac calls it after every task and the standard manager's flush drops its index of the classpath jars; directories are not indexed and are listed afresh anyway. The options are fixed:
- `-g -parameters -encoding UTF-8`: the enhancers read the local variable tables, and action binding reads the parameter names;
- `-proc:none -nowarn` and an empty `--processor-path`: without one, javac opens every classpath jar on each compile looking for plugins, 7 ms of each;
- `-Xpkginfo:always`: a package-info without annotations would otherwise get no class and be compiled again at every class load in its package;
- `java.source` as `-source`/`-target` when it is the running JDK's release, `--release` otherwise, which opens ct.sym on each compile, about 5 ms;
- at the JDK's own release only, what the JVM gives the classes it defines (`ApplicationCompiler.Jvm`): `--add-modules` for every boot-layer JDK module that exports to the application, `--add-exports <module>/<package>=ALL-UNNAMED` for each package the JVM exports to the application's unnamed module but not to everyone (what `--add-exports` and `--add-opens` give), and `--enable-preview` when the JVM runs with it, which a probe class marked as preview tells. ECJ read every class through Play's class loader and so compiled against the JDK as the JVM had it. The build script's `compileJava` arguments never reach this compile; only the JVM's own flags do. `--release` takes no `--add-exports` of a JDK module, so with an older `java.source` none reach the compile. A module from `--module-path` is not on javac's system path and is left out;
- `--enable-preview` for `java.enablePreview=true`.

The start's compile is shared by the JVMs that start an application from the same `tmp/` at once (PF-234), such as the test JVMs of one `./gradlew test` run, which before compiled every class of `app/` and `test/` with the same javac and options: on the Linux benchmark server, with a generated application of 1,600 classes, each JVM's classes phase took 6.8 s alone and 12.1 s at 8 JVMs. `play.classloading.SharedCompile`, called from `ApplicationClassloader.getAllClasses`, takes a file lock in `tmp/javac/` named after everything javac reads: the JDK (`Runtime.version()`, `java.home`), the compiler's options, every source on `Play.javaPath` with the file it is read from, and each class path entry (a jar by size and time, a directory by its files' sizes and times). The first JVM compiles, writes javac's output (`<key>.bin`: each class's name, source file and unenhanced bytes) and holds the lock while it enhances and defines every class, which writes `tmp/bytecode`; a JVM that waited registers each class from that output through `ApplicationClass.compiled`, exactly as a compile would have, nested classes and a file's second top-level class included, releases the lock, since both files are complete by then, and defines the enhanced classes from `tmp/bytecode`. Holding the lock through that define made the waiting JVMs go one at a time, 0.4 s each at 8 JVMs. That is safe because `loadApplicationClass` already defined a class from the bytecode cache whenever its hash matched, so the compile of such a class was thrown away anyway; skipping the compile instead of sharing it would lose the nested classes, which only javac's output names, and the unenhanced bytes the enhancers read. Only a JVM's first start shares: a DEV restart in the same JVM compiles what changed beside what it compiled before, which no other JVM has. A class compiled before the start's compile, as docviewer's `DocViewerPlugin` is while Play loads the plugins (in every DEV and test start), is read by javac as its class file, so the key holds its bytes and the output's copy of it is left alone; a gate that refused to share once any class was compiled never shared at all. Nothing is shared with `play.bytecodeCache=false` or a read-only `tmp/`. On the same server and application at 8 test JVMs, the classes phase went from 12.1 to 12.2 s in each JVM to 6.7 to 7.7 s from a cold `tmp/`, and each JVM's start from 13.1 to 13.3 s to 7.7 to 8.7 s. On a run with nothing changed since the last one no JVM compiles: 6.1 to 6.7 s became 0.7 to 1.2 s, and the task's wall time 10.6 s became 5.0. An output it cannot read or place, or one whose lengths the file does not hold, registers nothing and the JVM compiles on its own. So does a key that cannot be computed, such as a class path directory that cannot be listed or is deleted while it is walked: before the shared compile, such a start compiled, and it must not fail now. A JVM waits for the lock at most 60 s (`SharedCompile.waitLimitMs`, an INFO line after 3 s) and then compiles on its own, so a first JVM stopped at a breakpoint, suspended or deadlocked holds up no other start for long. `SharedCompileTest` holds the lock in a child JVM, because two threads of one JVM wait on its in-JVM lock and never reach the file lock: with the file lock taken on another file, its two cross-JVM cases fail. Other keys' outputs and locks are deleted after an hour. A DEV start shares in the same way with the next start whose sources, JDK and class path are unchanged. Guarded by `SharedCompileTest`; its case of a class path directory that cannot be listed skips on Windows, whose file systems have no POSIX permissions to make one.

Play's compile refuses a method reference to one of `GenericModel`'s static finder placeholders (PF-242): `count`, `findAll`, `all`, `deleteAll`, `findById`, `find`, `delete` and `create(String, Params)`, whatever the qualifier, `Book::findById` or `GenericModel::count`. Such a handle names `GenericModel`, the class that declares the method, under javac and ECJ alike, so it reaches the placeholder, which throws, and not the finder `JPAEnhancer` gives the entity; the entity's type is not in the bytecode for any enhancer to redirect it. `play.classloading.FinderReferenceCheck`, a javac `TaskListener` that `ApplicationCompiler.compile` adds to its task, looks at each top-level class after attribution and reports an ERROR at the reference with the lambda to write, whose parameters follow the overload it resolved to (`() -> Book.count()`, `(query, params) -> Book.count(query, params)`). The compile then fails as any error does: the DEV page at the line, a failed `play precompile`. It goes by what the reference resolved to, so an entity's own static method of the same name, an instance method such as `Post::create` on an instance, and `GenericModel`'s working static `create(...)` and `edit(...)` are untouched. It is a class of its own so that only a start that compiles loads it and the `jdk.compiler` types it uses. Gradle's `compileJava` has no such listener, by design. Guarded by four `ApplicationCompilerTest` cases, three of which fail without the listener.

One `StandardJavaFileManager` is shared, so compiles take turns (`synchronized`). Every javac task runs on one thread of its own, `play-javac`, which nothing interrupts; the caller waits, and an interrupt it gets meanwhile is set again when javac is done. javac reads the classpath's jars through the JDK's zip file system, an interrupt during a read closes a jar's channel for good, and the shared manager keeps the jar open, so one compile on an interrupted thread made every later compile of the JVM fail with "bad class file ... ClosedChannelException". A DEV reload was one: the request that restarts the application runs `Play.start()` on its own thread, and `Invoker.stop()`'s `shutdownNow()` interrupted that thread with the others, which it now leaves as it was. ECJ read classes through Play's class loader, which an interrupt does not touch. `ApplicationClassloader.detectChanges` compiles every changed class in one `compile` call before it enhances any. A javac task costs milliseconds of its own, 15 ms in an application with a 1,500-class package where ECJ took 1: a hundred changed classes took 3.6 s as one task each, and take 18 ms in one. javac also compiles try-with-resources differently from ECJ: its cleanup is a handler that catches `Throwable`, closes the resource and rethrows, where ECJ wrote a finally handler. `ControllersEnhancer` puts `if ($1 instanceof Result || $1 instanceof Suspend) throw $1;` at the start of every typed handler of a controller method, so that a user's `catch` cannot swallow a render, and on javac's cleanup handler that made a render inside the try leave before `close()`: the action leaked its connection, stream or lock, and an application's pool ran dry after as many requests as it had connections. `ControllersEnhancer.closesAndRethrows` leaves out a `Throwable` handler that keeps what it caught in a local the local variable table does not name, calls a no-argument `close()` and then throws that local, which is javac's shape; every catch of the source keeps the check, one that closes and rethrows only some throwables and an unnamed `catch (Exception _)` included. The check sits at the handler's own pc (`insertResultChecks`): javassist's `Handler.insertBefore` appended it at the end of the method, outside every exception range, so the Result it rethrew skipped each `finally` and `monitorexit` around the catch, with ECJ's bytecode too, and HotSpot threw `IllegalMonitorStateException` in place of the render. Three more shapes that both compilers emit are handled since: a field a constructor writes before `super()` (JEP 513) stays a plain `putfield` in `PropertiesEnhancer`, `SigEnhancer`'s static-initializer checksum reads an invokedynamic's bootstrap arguments, where a string concatenation keeps its literals, and `LocalvariablesNamesEnhancer` scans for stores from a variable's first instruction and reads `wide` ones (all guarded by `JavacEnhancersTest`). A compile that can emit nothing is therefore one to skip. Hibernate's ByteBuddy asks the loader for each proxy's name (`models.Order$HibernateProxy$...`) before it makes the proxy, `getJava` maps any name with a `$` to the top-level class's file, and that file was compiled again for each proxied entity at every start and restart: 1.2 s of every restart in an application of 45 entities. `ApplicationClass.isNestedNameItsFileDoesNotDeclare` refuses a nested name that the compile of its file, as the file is now, did not emit, since javac emits every class a file declares, and `doLoadApplicationClass` drops its entry, which `detectChanges` would otherwise take for an edited class (guarded by `DetectChangesCompileTest`). `BytecodeCache.hash` names javac's version, `java.source`, `java.enablePreview` and whether the JVM runs with `--enable-preview`, so no cached class of another compile is reused. A compile error is the first ERROR diagnostic, turned into a `CompilationException` with the file, the line and the inclusive end offset ECJ gave, which the DEV page marks. The measured reload times are under "The Java compiler" in `documentation/manual/production.textile`. Guarded by `ApplicationCompilerTest`, `JavacEnhancersTest`, `DetectChangesCompileTest`, `integration.JavacDevModeTest` (including a DEV JVM started with `--add-exports`, `--add-modules` and `--enable-preview` and no key), `InvokerVirtualThreadTest` (the reload's interrupt) and the gradle-plugin's `PreviewBothCompilesTest` (one class through `compileJava` and `playPrecompile` against the checkout's real framework, both class files at minor version 65535; it skips when `framework/play-<version>.jar` is missing).

`java.enablePreview=true` in `application.conf` is the one opt-in for preview features. Play's javac reads it from the configuration, and also compiles with `--enable-preview` when the JVM was given the flag another way. The plugin's `configurePreview` reads the bare key through `providers.fileContents`, so the configuration cache records the file, and adds `--enable-preview` to every `JavaCompile` task and the JVM option to every `Test` task. `confJvmArgs` and `conf_jvm_args` add `--enable-preview` for the key as the play id resolves it, so every Play JVM gets it: `registerPlayJvmTask` (playRun, playTest, playPrecompile, playEvolutions), `spawnPlay` (playStart, playRestart, playAotGen), `PlayAutotestTask` and `bundle-play.sh`. A class compiled with it carries minor version 65535, which the JVM loads only when started with the flag. Only the word `true`, in any case, turns it on; Play refuses any other value but `false` when it compiles. Guarded by `PreviewOptInTest` (compileJava and compileTestJava, every launch site, an AOT training run and a start from its cache with `-XX:AOTMode=on`), `PreviewBothCompilesTest`, `ConfJvmArgsTest` and the parity case in `BundleLauncherTest`.

### Precompilation and packaged artifacts

`play precompile` (and the `playBundle`/`playDist` tasks that depend on it) boots the framework once with `-Dprecompile=yes` under `play.id=test`, writing enhanced bytecode to `precompiled/java/` and parsed templates to `precompiled/templates/`. `precompiled/` is packaged into the production artifact; in a self-contained bundle it is force-loaded at startup (`-Dprecompiled=true` → `ApplicationClassloader.scanPrecompiled` loads *every* class under `precompiled/java/`). Two things are therefore deliberately kept **out** of `precompiled/`, even though precompile still *compiles* them so build errors surface (since 1.13.26):

- **`test/` sources** — compiled (a broken test fails the build — the gate) but their bytecode is not written. `ApplicationClasses.enhance()` skips the `precompiled/java/` write for any class whose source is under a `test/` root (`isTestSource()`, checked against `Play.roots`). Keeps test code — and its JUnit dependency — off the production classpath, where `scanPrecompiled` would otherwise force-load it at boot.
- **The `testrunner` module** — `Play.loadModules()` skips the `_testrunner` auto-mount when `-Dprecompile` is set, so its controllers never enter `javaPath` and its views never enter `templatesPath`, keeping both out of `precompiled/java/` and `precompiled/templates/`. The `test/` compile gate is unaffected: `TestRunnerPlugin` loads from `play-testrunner.jar` (on the classpath, not via the mount) and its `onLoad()` adds `test/` to `javaPath` independently.

`play bundle` is self-contained (framework jar + deps + modules + a bundled `play` launcher; no Gradle at runtime), so `PlayBundleTask` must carry each declared module's non-jar resources — `play.plugins` descriptors, `public/` assets, `conf/` — by walking `modules/*/` and shipping everything except lib jars (handled separately). Without them a module's plugin never registers at prod startup (`getResources("play.plugins")` finds nothing — e.g. docviewer's `/@docs` 404s). It also carries the framework's default messages at `framework/resources/messages` (PF-181): `MessagesPlugin` reads them from `Play.frameworkPath` — which the launcher points at the bundle's `framework/` directory — not from the classpath, so without the file `validation.*` and `since.*` render as raw keys. `play dist` is the lean alternative (app source + `precompiled/` + SPA, no framework/modules/launcher) and ships **no** `modules/`: it is deployed into a Gradle context where `extractPlayModules` re-populates them at launch, so it neither needs nor has the bundle's resource-packaging concern.

A bundle and a dist carry the application's precompiled classes as **one jar, `precompiled/classes.jar`**; `play precompile` and a start from the working copy keep the `precompiled/java` tree, and nothing may write a jar into the working copy's `precompiled/`. The jar is packed inside the `PlayBundleTask`/`PlayDistTask` action (`addPrecompiledJar` in `Play1Plugin.kt`), not by a task they depend on: an app's build step that rewrites `precompiled/java` before packaging (a ProGuard debug-strip is one) is a dependency of the packaging task and has therefore always run by then, whereas a separate jar task in the default graph would have no order against it and could ship unprocessed classes. `.distignore` prefixes under `precompiled/java/` filter what goes into the jar. Entries are sorted, stored and stamped with one fixed time, so the same classes give the same bytes and a start reads them without inflating. For jar-to-jar processing there is the opt-in `playPrecompiledJar` task (`build/play/precompiled/classes.jar`) and the `precompiledJar` property on both packaging tasks, which ships a supplied jar as it is. On the framework side `play.classloading.PrecompiledJar` reads the jar: `ApplicationClasses.precompiledJar()` looks for it once, and `ApplicationClassloader` (`precompiledCode`, and the scan in `getAllClasses`) and `Enhancer.ApplicationClassesClasspath` take class bytes from it when it exists, else from the tree. The jar wins over a tree beside it, which is the leftover of an older install. It is deliberately **not on the JVM classpath**: Play's loader still defines the classes, which the class registry (`Play.classes`) and `conf/` lookups through application classes depend on. The loader closes the jar after the start-up scan. Precompiled templates stay files. Guarded by `PrecompiledJarTest`, `BootTimingsLineTest.precompiledProdBootReadsItsClassesFromTheJarABundleOrDistCarries` and the plugin's `PrecompiledJarPackagingTest`.

Every enhancer that grows a method leaves the Code attribute's type annotations behind (PF-187): Javassist's `CodeIterator` gap insertion shifts the exception table, line numbers, local variable tables and stack maps, but `TypeAnnotationsAttribute` has no shift, so a `TYPE_USE` annotation on a local, a cast, an `instanceof` or a `new` (`localvar_target`, `offset_target`, `type_argument_target`) keeps its pre-enhancement offsets. The JVM and reflection never read those, so the running app is unaffected, but a tool that validates them (ProGuard over `precompiled/java`, as an application's release strip does) rejects the class with "Invalid instruction offset". `play.classloading.enhancers.CodeTypeAnnotations.dropWhereCodeMoved` runs once at the end of `ApplicationClass.enhance()`, after `Play.pluginCollection.enhance`, so it covers every enhancer, plugins' included, and both the in-JVM define and the precompiled write: for each method whose code length differs from its length in `javaByteCode` it removes `RuntimeVisibleTypeAnnotations` and `RuntimeInvisibleTypeAnnotations` from the Code attribute. Gaps only grow code, so an unchanged length means no offset moved and the method keeps its annotations; a method that grew loses all of its Code-level type annotations, ranges the gap did not reach included, because Javassist keeps no record of where its gaps went. Type annotations on `method_info`, `field_info` and the class are never touched (`getAnnotatedReturnType` reads those). A class with no Code-level type annotations costs one parse and no write. Do not add a shift instead of the drop without a record of the gap positions. Guarded by `CodeTypeAnnotationsTest`, which enhances `CodeTypeAnnotationsFixture` through `ApplicationClass.enhance()` with the real `PropertiesEnhancer` and reads the result with the JDK ClassFile API.

A bundle's `.classpath` holds **jars only** (PF-180): the JDK refuses to write an AOT cache while a non-empty directory is on the classpath, and `conf/` used to be the first entry. `PlayBundleTask` must never list a directory there (guarded by `BundleClasspathTest`). Nothing in the framework may therefore rely on `conf/` being on the JVM classpath: `Logger.LoggerInit.preferConfFile` and `Play.initStaticStuff` look in `<application.path>/conf` themselves when the classpath has no such resource, or has it only inside a jar, and everything else reaches `conf/` through `ApplicationClassloader` (`Play.init` adds it to `javaPath`). A new `getResource` on a framework class or on the system loader for a file an app keeps in `conf/` would work under an ordinary Gradle start, whose classpath still starts with `conf/`, and fail silently in a bundle and in a Gradle start from an AOT cache (PF-185, below). Third-party libraries that resolve through their own loader no longer see `conf/` in a bundle; the upgrade note is in `documentation/manual/deployment.textile` (`#bundle-classpath`).

`bundle-play.sh` has `aot-gen`: a training run with exactly `run`'s JVM options plus `-XX:AOTCacheOutput=app.aot.new`. It waits on the port (`--http.port`, else `http.port` through `conf_value`, else 9000, and passes that port on), requests `GET /` over bash's `/dev/tcp` (no curl), or each path of `aot.training.paths` in order (PF-258: a comma-separated list, each starting with `/` and free of whitespace, refused before a JVM starts otherwise; `aot_training_paths` and Kotlin's `trainingPaths` read it alike), stops the JVM with SIGTERM because the cache is written only on a normal exit, and moves the file to `app.aot` only when the JVM has removed its `<output>.config` recording, which is its sign that the cache-assembly child process finished (a killed child leaves a truncated file and the recording). It never reads or writes the pid file. Under Git Bash, MSYS2 and Cygwin it refuses: `kill` is a hard kill for a native `java.exe`. `run` and `start` add `-XX:AOTCache=app.aot` when the file exists, ahead of the JUL arg so that conf and command line win, and leave it out when either carries an option the JVM refuses to start with next to it (`-Xshare:*`, `-XX:SharedArchiveFile`, `-XX:SharedClassListFile`, `-XX:DumpLoadedClassList`, `-XX:AOTCacheOutput`, `-XX:AOTConfiguration`, `-XX:AOTMode=record|create`). The cache is tied to the JDK build, the collector and heap layout, the module options, the jars' paths, sizes and mtimes, and OS and CPU, so it is never part of the zip. Guarded by the `aot-gen` and AOT cases in `BundleLauncherTest`, one of which trains a real JVM. GraalVM native image is rejected on the record, with four re-evaluation triggers, in `docs/adr/0001-reject-graalvm-native-image.md`: do not add a native-image mode, reachability metadata or a GraalVM toolchain.

A precompiled start through Gradle, from a working copy or a dist install, has the same cache (PF-185), at `build/play/aot/app.aot` in the application. `isPrecompiledStart` reads the JVM arguments as the JVM and `Server.main` do: the last `-Dprecompiled` wins and only `true` counts. For such a start `spawnPlay` (`playStart`, `playRestart`) and `playRun` add `-XX:AOTCache=<the file>` when it exists, in front of the conf and command-line options, and **only a JVM that is given that option, or the training run's `-XX:AOTCacheOutput`, gets a classpath without directories**. The directories are `conf/` and, through `sourceSets.main.runtimeClasspath`, `build/classes/java/main` and `build/resources/main`; the JVM writes no cache with one of them present and accepts a cache only on the classpath it was written with. An application that never trains is therefore launched exactly as before, precompiled or not, and a start that compiles always keeps the directories, which javassist reads (PF-94). Do not widen the classpath change to every precompiled start: it takes `conf/` away from libraries that look there through the system class loader, and only an application that asked for a cache, by running `play aot-gen`, should pay that. `playRun` decides in a `doFirst`, because only at execution time does a `JavaExec` hold what a build script added, and the action must not touch `project` (the configuration cache). A `JavaExec` also moves `-D` and `-Xmx` arguments to slots of its own on the command line, so a test of argument order there has to use `-XX:` options. `aotCacheArg` is `aot_cache_arg` of `bundle-play.sh` written a second time, and `BundleLauncherTest` runs both over one list of options: change them together. `playAotGen` (`play aot-gen` in the shim) is the bundle's training run on top of `spawnPlay`, so its command line is that of a start from the cache with `-XX:AOTCacheOutput` in place of `-XX:AOTCache`: the same wait on the port, the same `GET /` or `aot.training.paths`, SIGTERM through `Process.destroy()`, and the cache moved into place only when the JVM's `<output>.config` recording is gone. It adds `-Dprecompiled=true` when its arguments lack it, refuses without `precompiled/java` or `precompiled/classes.jar`, and deliberately depends on neither `playPrecompile` nor `compileJava`: precompiling deletes `precompiled/` under an instance that may be running from it. It refuses on Windows, where `destroy()` is a hard kill. The cache lives under Gradle's build directory on purpose, and nothing the plugin generates for an application belongs loose in its root: every application's `.gitignore` already excludes `build/`, which keeps a hundred-megabyte file out of version control without a new line there and out of `playDist` and `playBundle`, which ship what `git ls-files` returns. `playPrecompile` leaves it alone and `gradle clean` removes it. A bundle is not a working copy and keeps its `app.aot` in its root. A test that needs a JVM to end without a cache has to kill it, because `Runtime.halt` still runs the cache assembly. Guarded by `PrecompiledStartTest`, the parity case in `BundleLauncherTest`, `PrecompiledJarPackagingTest` and `PlayShimTest`.

The Nuxt SPA build (`pnpm install` + `pnpm run generate` → copy `frontend/.output/public` to `public/spa`) is the registered `playFrontendSpa` task that both packaging tasks `dependsOn`, not a helper called from their action bodies (PF-169). Gradle's run-each-task-at-most-once rule applies to the task graph only, so as an in-action call it ran twice for `gradle playDist playBundle` — the single invocation a CI packaging stage naturally uses. An `onlyIf` on `frontend/` being a directory keeps frontend-less apps unaffected. It deliberately keeps `outputs.upToDateWhen { false }` and declares **no** inputs/outputs: a Nuxt build legitimately reads files outside `frontend/` (a `nuxt.config.ts` can widen Vite's `fs.allow` to import docs from the repo root) as well as non-file inputs like the Node and corepack-pinned pnpm versions, so an input set scoped to `frontend/` would report UP-TO-DATE and silently ship a stale SPA in a release artifact. If the build cost ever justifies skipping, prefer an explicit `-P` opt-in over an inferred up-to-date check. The built SPA is served at the **site root** by the reverse proxy, not through Play's `/public/` static route: Nuxt generates it with `app.baseURL: "/"`, so its markup references `/_nuxt/...` and opening `/public/spa/index.html` loads the page but 404s every asset. That is by design, not a defect — see "Serving the Nuxt frontend" in `documentation/manual/deployment.textile`.

The skel's frontend is a single-page app, `ssr: false` (PF-208), and that is deliberate, not a default to restore: the fork ships `nuxt generate`'s static output and no Node server, and with `ssr: true` the generate step prerenders each page at build time, so the skel's `useFetch('/api/status')` froze whatever backend answered on the build machine into `_payload.json` and the deployed page never asked again. The server-side bundle that `ssr: true` builds is also where Nuxt's own build notices come from (an esbuild BigInt literal, an unused `isMethod` import), which is why an application already on `ssr: false` never printed them. Prerendering stays available to an application whose config has no `ssr` key, and an explicit `ssr: true` gets Nuxt's server packaged and run (next paragraph); the manual's "Serving the Nuxt frontend" says how to use each.

A frontend whose config sets `ssr: true` itself gets Nuxt's server packaged and run beside Play (PF-209). `playFrontendSpa` reads the config with Nuxt's own loader (`nuxt-ssr-mode.mjs`, run as `pnpm exec node` after `pnpm install`, through the app's installed nuxt; PF-214: a bare `node` from Gradle is looked up on the PATH the daemon started with, and the check runs for every frontend, single-page apps included), and only a layer that sets `ssr` counts: Nuxt resolves an absent key to true, and an older scaffold without one keeps the static build (PF-210). `pnpm run build` then leaves the server at `frontend/.output`, never under `public/`, which Play serves as files, and the build writes `play1-server.mjs` (how the launchers start it) and `play1.json` (Nitro's `engines.node`) beside it. `forcedBuildOutputRoots` puts `frontend/.output` into the dist and the bundle only when it holds `server/index.mjs`, whose presence is also what tells the launchers an application runs Nuxt's server. The skel's `server/api/[...path].ts` forwards `/api` to the runtime config's `playBackendUrl`, which `NUXT_PLAY_BACKEND_URL` overrides where the server starts, because `nuxt.config` is evaluated once, at build time, and a build-time proxy target answered 502 once Play's port differed (PF-211); under `pnpm dev`, `nitro.devProxy` answers `/api` first. A fetch made while a page renders passes the browser's cookies to Play, but Nuxt does not copy a `Set-Cookie` in Play's answer into the page's response (none reached the browser when a server-side fetch bumped a session counter). The skel's `useApi` therefore copies them, with h3's `appendResponseHeader` in an `onResponse` hook that acts on the server only, Nuxt's documented pattern, and the index page fetches through it; a plain `useFetch` still drops them. `h3` is no dependency of the skel, but Nuxt resolves it for app code even under pnpm's strict layout. The bundle launcher (PF-212) and the Gradle start tasks (PF-213) share one set of rules, written twice: `frontend_preflight`, `frontend_env`, `wait_for_play` and `stop_frontend_pid` in `bundle-play.sh`, `frontendPreflight`, `frontendLaunch`, `waitForPlay` and `stopFrontendProcess` in `Play1Plugin.kt`, so change them together. Check Node (`play1-server.mjs --check`) before anything starts; start Play; wait until it listens (`PLAY_FRONTEND_WAIT`); start Nuxt's server on `frontend.host`:`frontend.port` with `certs/.env` and `NUXT_PLAY_BACKEND_URL`; stop it first, through its stop file, which `play1-server.mjs` answers by running the server's own SIGTERM handler. A file and not a signal, because no signal reaches a native node.exe from another process on Windows. `PLAY_NODE` names the Node. The Gradle tasks do this for a PROD start only: a working copy that has made an SSR build still develops under `pnpm dev`, which wants port 3000 too. `playRun` runs it through the `NuxtServerService` build service, whose `close()` stops it when a run fails or is cancelled. Guarded by `NuxtSsrBuildTest`, the SSR case of `PrecompiledJarPackagingTest`, the PF-212 section of `BundleLauncherTest` and `NuxtServerStartTest`. Their fake Play listens only after `-Dpf212.listen.delay` or `-Dpf213.listen.delay`, so that starting Nuxt's server without waiting cannot pass by winning the race. The launcher's Windows leg runs only on CI (`windows-latest`), and `NuxtServerStartTest` is off on Windows, as `PrecompiledStartTest` is. Windows support for SSR is partial, by decision (2026-11-17): the launcher cases have passed under Git Bash with a stub node, but a real node.exe, the stop file against a real Nuxt server and the Gradle start tasks have never run there. Fix what users report; do not describe it as verified.

An application's pnpm follows the framework's (PF-207), which is the `packageManager` pin of `resources/nuxt-skel/package.json`: Renovate bumps it and `/renovate` gates it with a scratch build of the skel. The plugin's `processResources` copies that file into the jar (`play/gradle/nuxt-skel-package.json`), so an application follows the release it builds against, not whatever a working copy of the fork holds; `PnpmPinTest` fails when the copy and the skel disagree. `playFrontendSpa` logs one warning when `frontend/package.json` pins another pnpm version or none, and builds on: a warning, not a failure, by decision. `playPnpmSync` (`play pnpm-sync`) writes the pin and always runs `pnpm install` after it, because pnpm 12 records itself in `pnpm-lock.yaml` (`packageManagerDependencies`, with every per-platform binary's integrity), and a pin moved without the install fails the next `pnpm install --frozen-lockfile`, which an application's CI runs. Both tasks run pnpm through a `pnpm` property ("pnpm" by convention): `PnpmSyncTaskTest` sets a stub's absolute path there, because the JDK looks a bare command up on the PATH the TestKit daemon started with, which `withEnvironment` cannot change.

An application's Gradle wrapper follows the framework's in the same way (PF-216), which is the fork's own `gradle/wrapper/gradle-wrapper.properties`: its `distributionUrl` and `distributionSha256Sum`. The wrapper checks that checksum only when it downloads a distribution, so a bump on an application's Renovate runner, which has no framework and cannot run `./gradlew`, moved `distributionUrl` and kept the old sum, and only an empty Gradle home found it: an application's Docker image build, at its 9.8.2 and 9.9.1 bumps. The plugin's `processResources` copies that file into the jar (`play/gradle/wrapper/`) with the fork's `gradle-wrapper.jar`, `gradlew` and `gradlew.bat`, so an application follows the release it builds against; `GradleWrapperPinTest` fails when a copy and the repo's file disagree. While the root project's wrapper names another distribution, or the framework's with another checksum or none, every build logs one warning while it configures and goes on: a warning, not a failure, by decision. An application without the file gets none. The plugin reads the file through `providers.fileContents`, so the configuration cache records it as an input: a changed wrapper reconfigures and that build warns, and a build that reuses the cache prints nothing, as with PF-194's warnings. `playGradleSync` (`play gradle-sync`) puts the fork's two lines in place of the application's, adds a missing checksum above `distributionUrl`, keeps every other line, and reads the result back, failing with the two lines to set by hand when the file cannot be rewritten line by line (a value continued onto the next line). It writes the fork's jar and scripts, the ones `playNewApp` copies, and not those of the Gradle that runs it: Gradle's own `wrapper` task writes the running Gradle's, which is why Gradle tells you to run that task twice. The files are written in place, as the `wrapper` task writes them, because the running Gradle was started from them. Guarded by `GradleWrapperPinTest`, `GradleSyncTaskTest` (including a configuration-cache run) and `PlayShimTest`.
