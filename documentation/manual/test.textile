h1. Test your application

Creating automatic test suites for your application is a good way to make it robust. It allows you to work in a very agile way.

Play tests are built using "JUnit":http://www.junit.org/.

h2. <a name="writing">Writing tests</a>

The tests must be created in the @test/@ directory. This folder will only be added to the sources path when the application is run in @test@ mode. You can write two different kinds of tests.

h3. Unit test

A unit test is written using JUnit. In this kind of test you can test the model of your application (including some utilities). 

Here is an example of a Unit test:

bc. import play.test.*;
import org.junit.*;
 
public class MyTest extends UnitTest {
     
    @Test
    public void aTest() {
        assertEquals(2, 1 + 1); // A really important thing to test
    }
 
    @Test
    public void testUsers() {
        assertEquals(3, Users.count()); 
    }
}

h3. Functional test

A functional test is written using JUnit. In this kind of test you can test your application by accessing directly the controller objects.

Here is an example of a Functional test:

bc. import play.test.*;
import play.mvc.*;
import play.mvc.Http.*;
import org.junit.*;
 
public class ApplicationTest extends FunctionalTest {
     
    @Test
    public void testTheHomePage() {
        Response response = GET("/");
        assertStatus(200, response);
    }
     
}

Using the @renderArgs()@ method, you can also get direct access to the arguments passed to the view, instead of having to make assertions about the response itself.  For example:

bc. @Test
public void testUserIsFoundAndPassedToView() {
    Response response = POST("/user/find?name=mark&dob=18011977");
    assertThat(renderArgs("user"), is(notNullValue()));
    User user = (User) renderArgs("user");
    assertThat(user.name, is("mark"));
}

h3. CleanTest Annotation

Some Unit/Functional tests may need to (or should not) access these ThreadLocal MVC objects:
* Response,
* Request,
* RenderArgs,

By default these objects will be created and you can directly access them.
The CleanTest annotation enables you to change this default behaviour (a use 
case would be to test some code that will be used in a Job context and thus 
doesn't have access to these objects).   


bc.  Request request = Request.current();
// some code to use request
     
Response response = Response.current();
// some code to use response
      
RenderArgs renderArgs = RenderArgs.current();
// some code to use renderArgs

In order to control the access to these parameters, you can use the <code>@CleanTest</code> on the test class.

bc. @CleanTest(removeCurrent= true, createDefault=false)
public class FunctionalTestCleanTest extends FunctionalTest {
    @Test
    public void testParam(){
        Request request = Request.current();
        assertNull(request);
     
        Response response = Response.current();
        assertNull(response);
      
        RenderArgs renderArgs = RenderArgs.current();
        assertNull(renderArgs);
     }  
}

This annotation has the following properties:

* **removeCurrent**: Indicate if current MVC objects will be removed or not
* **createDefault**: Indicate if current MVC objects will be created or not


h2. <a name="fixtures">Fixtures</a>

When you run tests, you need to have stable data for your application. The simplest way is to reset your database before each test.

The @play.test.Fixtures@ class helps you to manipulate your database and to inject test data. You typically use it in a <code>@Before</code> method of a JUnit test.

bc. @Before
public void setUp() {
    Fixtures.deleteDatabase();
}

p(note). @deleteDatabase@ deletes with plain SQL, which Hibernate does not see, so it also evicts every region of the second-level cache: entities, collections and cached query results. The eviction covers the whole JVM, so a test class running at the same time reloads its cached entities from the database.

To import data, it is simpler to define them in a YAML file that the Fixtures helper can automatically import.

bc. # Test data
 
Company(google):
   name:    Google
 
Company(zen):
   name:    Zenexity
 
User(guillaume):
   name:    guillaume
   company: zen

And then: 

bc. @Before
public void setUp() {
    Fixtures.deleteDatabase();
    Fixtures.loadModels("data.yml");
}

p(note). You can read more about Play and YAML in the "YAML manual page":yaml.

p(note). You can use @loadModels@ instead of @load@; the two parameters are synonyms.

Sometimes it is convenient to split data into several YAML files. You can load fixtures from multiple files at once:

bc. Fixtures.loadModels("users.yml", "roles.yml", "permissions.yml");

p(note). The fixture file will be loaded as a Template by default.
To avoid this, you can use @Fixtures.loadModels(boolean loadAsTemplate, String name)@ with @loadAsTemplate@ set to @false@.

h2. <a name="transactions">Transactions in tests</a>

By default a test runs inside a JPA transaction it did not open. The test runner that @play test@ and @play autotest@ use runs each test class in a job, and every test of the class reads and writes in that job's transaction, which commits only when the whole class has finished. A request that a functional test sends runs in a transaction of its own, so it does not see what the test saved:

bc. @Test
public void theRequestDoesNotSeeIt() {
    User bob = new User("bob").save();
    assertStatus(404, GET("/users/" + bob.id)); // bob is not committed yet
}

With @play.test.transaction=none@ in @application.conf@, the code of a test class, from its constructor and its <code>@BeforeAll</code> methods to its tests and its <code>@AfterAll</code> methods, runs with no transaction open, as it does in a plain JUnit setup. The key takes @ambient@, the default, or @none@, in any letter case; the application refuses to start with any other value.

Once the setting is on, a test does these things for itself:

* It opens and commits a transaction around what it reads or writes through JPA: @save()@, @findById()@, @JPA.em()@ and @DB.getConnection()@ all need one. @JPA.withTransaction("default", false, () -> ...)@ commits when the block returns and rolls back when it throws. Outside one, these fail with a message that says so.
* It resets the database, because what it commits stays there for the next test. @Fixtures@ called with no transaction open, as from a <code>@BeforeEach</code> method, opens and commits one of its own, so what it deletes and loads is in the database when the test's requests run.
* It opens a transaction around a job it calls directly, with @call()@ or @run()@: in the test runner such a job runs as part of the test, with no transaction. A job started with @now()@ or @in()@ runs in a transaction of its own, as does every request a functional test sends.

bc. @BeforeEach
public void setUp() {
    Fixtures.deleteDatabase();
}
 
@Test
public void theRequestSeesWhatTheTestCommitted() throws Throwable {
    User bob = JPA.withTransaction("default", false, () -> new User("bob").save());
    assertStatus(200, GET("/users/" + bob.id));
}

h2. <a name="running">Running the tests</a>

To run the tests, you must run your application in @test@ mode using the @play test@ command:

bc. play test myapp

In this mode, Play will automatically load the @testrunner@ module. This module provides a Web-based test runner, available at the "http://localhost:9000/@tests":http://localhost:9000/@tests URL.

!images/test-runner!

When you run a test, the result is saved into the @/test-result@ directory of your application.

On the test runner page, each test is a link. You can ‘right click’ and ‘Open in a new tab’, to run the test directly outside of the test-runner.

When you run tests this way, Play will start with a special @test@ framework ID. So you can define special configurations in the @application.conf@ file.

If you want several different test configurations, you can use framework IDs matching the pattern @test-?.*@ (e.g: @test-special@).

If you use a framework ID other then the default @test@, you must make sure ALL test configuration in @application.conf@ is available with that framework ID. When launching test with special test framework ID you do it like this: @play test --%test-your-special-id@

For example:

bc. %test.db=mem
%test.jpa.ddl=create-drop

h2. <a name="continuous">Continuous integration, and running the tests automatically</a>

The @autotest@ command does the same as the @test@ command, but it automatically launches a headless browser via Firephoque, runs all the tests, and stops:

bc. play autotest myapp

This is a useful command if you want to set up a continuous integration system.

After the run, all results are saved to the @/test-result@ directory. Moreover, this directory contains a marker file (either @result.failed@ or @result.passed@) for the test suite’s final result. Finally, this directory contains all the logs, in an @application.log@ file.

The command's exit status is the result to rely on: it is non-zero when any test failed or ended in error, even when @result.passed@ is there. The marker is written by whichever server answers on the test port, so a run that shares its port with another one can find the other run's marker beside its own failures. If the server on the port turns out to be another application's, @play autotest@ stops before it runs or deletes anything and says so. Give each checkout that runs tests at the same time a port of its own, for example with @PLAY_TEST_PORT@ in its @certs/.env@.

So setting up a continuous integration system to test your application could be:

* Checkout the latest version of your application
* Run @play autotest myapp@
* Wait for the end of the process
* Check its exit status: zero only when every test passed

Run these steps in a CRON tab, and you’re done!

On a CI server the @play@ command runs Gradle without its daemon: when @JENKINS_URL@ is set, or @CI@ is set to anything but @false@ or @0@, every command gets @--no-daemon@. A CI server usually runs every build as one user, so builds that overlap share Gradle's daemons, and Jenkins ends every process a build started when that build ends. That includes a daemon another build is using at that moment, which then fails with "Gradle build daemon disappeared unexpectedly". @PLAY_GRADLE_DAEMON=true@ keeps the daemon on a CI server, and @PLAY_GRADLE_DAEMON=false@ turns it off anywhere. Steps that call @./gradlew@ directly are not covered: for those, set @org.gradle.daemon=false@ in the CI user's @~/.gradle/gradle.properties@.

You can change the web browser compatibility mode used by the headless browser by configuring "headlessBrowser":configuration#headlessBrowser.
