h1. Dependency management

Play 1.13 applications use "Gradle":https://gradle.org/ for dependency
resolution. Each application has a @build.gradle.kts@ at its root that
declares its Java/Kotlin dependencies, repositories, and Play modules.

h2. <a name="declaring">Declaring application dependencies</a>

Add dependencies to the @dependencies@ block in @build.gradle.kts@:

bc. dependencies {
    implementation("org.apache.commons:commons-csv:1.14.1")
    implementation("com.google.guava:guava:33.0.0-jre")
}

Repositories are declared once at the top of the file:

bc. repositories {
    mavenCentral()
}


h2. <a name="modules">Loading Play modules</a>

Play's built-in modules (@testrunner@, @docviewer@) are auto-loaded by the
Play 1 plugin and require no explicit declaration. Third-party modules can
be added via the plugin's DSL:

bc. plugins {
    id("org.playframework.play1")
}

play1 {
    modules("third-party-module")
}

The plugin extracts each declared module into the application's @modules/@
directory at build time. Module overlays (the legacy @override(f, t)@
mechanism) work transparently because modules are real directories on disk.


h2. <a name="shipped">Libraries the framework ships</a>

The framework ships its own dependencies in @framework/lib/@: Netty,
Hibernate, Jackson, OkHttp, Log4j and others. Your application compiles and
runs against those copies, and the Play 1 plugin keeps Gradle from resolving
a second copy of any of them. It excludes them from your application's
dependencies, whether you declare them or another library brings them in. A
declaration of one of them therefore has no effect, and the build says so:

bc. ~ WARNING: implementation("com.squareup.okhttp3:okhttp-jvm:5.5.0") has no effect: the application compiles and runs against com.squareup.okhttp3:okhttp-jvm 5.5.1 from framework/lib. Remove the declaration, or add "com.squareup.okhttp3:okhttp-jvm" to play1 { appManagedLibraries(...) } to keep the application's version.

A library that reached your application only through one of those leaves
with it. The framework ships what it uses itself, which is not always
everything the library would bring in, so if your code needs such a
library, declare it. Comparing @play classpath@ before and after an upgrade
shows what left.

To keep your own version of such a library, list it as @group:artifact@ in
@appManagedLibraries@. The plugin then leaves the framework's jar for it off
every classpath and out of @play bundle@, and Gradle resolves your version
like any other dependency:

bc. play1 {
    appManagedLibraries("com.squareup.okhttp3:okhttp-jvm")
}

The framework was built and tested against its own version, so take a
library over only when you need a different one. @play classpath@ shows the
result.


h2. <a name="resolving">Resolving dependencies</a>

Gradle resolves dependencies the first time you run any @play@ command
(@play run@, @play test@, etc.) and re-resolves whenever @build.gradle.kts@
changes. To inspect the resolved classpath:

bc. play classpath

To list resolved dependencies in tree form:

bc. ./gradlew dependencies

To force a re-resolve (e.g. after editing @build.gradle.kts@):

bc. ./gradlew --refresh-dependencies <task>


h2. <a name="framework">Framework dependencies</a>

The framework's own build (under @framework/@) still uses Apache Ivy with a
declarative manifest at @framework/dependencies.yml@. This is internal: Play 1
fork maintainers run @ant resolve@ to update @framework/lib/@. Application
authors never touch this file.
