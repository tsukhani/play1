h1. Dependency management

Play 1.13 applications use "Gradle":https://gradle.org/ for dependency
resolution. Each application has a @build.gradle.kts@ at its root that
declares its Java/Kotlin dependencies, repositories, and Play modules.

h2. <a name="declaring">Declaring application dependencies</a>

Add dependencies to the @dependencies@ block in @build.gradle.kts@:

bc. dependencies {
    implementation("org.apache.commons:commons-csv:1.14.1")
    implementation("com.google.guava:guava:33.0.0-jre")
}

Repositories are declared once at the top of the file:

bc. repositories {
    mavenCentral()
}


h2. <a name="modules">Loading Play modules</a>

Play's built-in modules (@testrunner@, @docviewer@) are auto-loaded by the
Play 1 plugin and require no explicit declaration. Third-party modules can
be added via the plugin's DSL:

bc. plugins {
    id("org.playframework.play1")
}

play1 {
    modules("third-party-module")
}

The plugin extracts each declared module into the application's @modules/@
directory at build time. Module overlays (the legacy @override(f, t)@
mechanism) work transparently because modules are real directories on disk.


h2. <a name="shipped">Libraries the framework ships</a>

The framework ships its own dependencies in @framework/lib/@: Netty,
Hibernate, Jackson, OkHttp, Log4j and others. Your application compiles and
runs against those copies, and the Play 1 plugin keeps Gradle from resolving
a second copy of any of them. It excludes them from your application's
dependencies, whether you declare them or another library brings them in. A
declaration of one of them therefore has no effect, and the build says so:

bc. ~ WARNING: implementation("com.squareup.okhttp3:okhttp-jvm:5.5.0") has no effect: the application compiles and runs against com.squareup.okhttp3:okhttp-jvm 5.5.1 from framework/lib. Remove the declaration, or add "com.squareup.okhttp3:okhttp-jvm" to play1 { appManagedLibraries(...) } to keep the application's version.

A library that reached your application only through one of those leaves
with it. The framework ships what it uses itself, which is not always
everything the library would bring in, so if your code needs such a
library, declare it. Comparing @play classpath@ before and after an upgrade
shows what left.

To keep your own version of such a library, list it as @group:artifact@ in
@appManagedLibraries@. The plugin then leaves the framework's jar for it off
every classpath and out of @play bundle@, and Gradle resolves your version
like any other dependency:

bc. play1 {
    appManagedLibraries("com.squareup.okhttp3:okhttp-jvm")
}

The framework was built and tested against its own version, so take a
library over only when you need a different one. @play classpath@ shows the
result.

A library your dependencies bring in may have been built against a newer
version of one of these libraries than the framework ships. It then runs on
the framework's copy, and fails with @NoSuchMethodError@ or
@NoClassDefFoundError@ when it reaches something the older copy lacks. The
plugin reads the versions your dependencies ask for, and warns once for each
library asked for above the framework's version, or through a range the
framework's version is outside of:

bc. ~ WARNING: org.apache.tika:tika-parser-xml-module:4.1.0 asks for commons-codec:commons-codec 1.22.1, but framework/lib ships 1.22.0, which it runs on. Upgrade the framework's copy, or add "commons-codec:commons-codec" to play1 { appManagedLibraries(...) } to keep the application's version.

Gradle prints no warnings under @-q@. To fail the build on such a request
instead, as a CI build may want to, set @failOnNewerLibraryRequests@. The
property @-PfailOnNewerLibraryRequests=true@ (or @=false@) overrides the
build script for one build:

bc. play1 {
    failOnNewerLibraryRequests = true
}

A member of one of these library families that the framework does not ship,
such as @mockwebserver3@ beside OkHttp or @jackson-dataformat-csv@ beside
Jackson, needs the version that matches the framework's. With
@importFrameworkBoms@ the plugin imports the BOM of each family the framework
ships, at the framework's version, and you declare such a library without a
version:

bc. play1 {
    importFrameworkBoms = true
}

dependencies {
    testImplementation("com.squareup.okhttp3:mockwebserver3")
}

The families are OkHttp, Okio, Jackson, Netty, Micrometer, the Prometheus
client, Log4j, Kotlin, Groovy, JUnit, SLF4J, ASM, Bouncy Castle and Swagger.
Gradle resolves the highest version anything asks for, so a BOM also raises
a family member you declare at a lower version to the framework's. Listing a
family's main library in @appManagedLibraries@, such as
@com.squareup.okhttp3:okhttp-jvm@ for OkHttp or
@com.fasterxml.jackson.core:jackson-databind@ for Jackson, leaves that
family's BOM out, because the family's version is then yours.


h2. <a name="scanning">Scanning the framework's libraries for vulnerabilities</a>

A vulnerability scanner that reads what Gradle resolves does not see the
libraries in @framework/lib/@, because your application no longer resolves
them. The framework scans every jar it ships before each release, with
"OWASP dependency-check":https://dependency-check.github.io/DependencyCheck/
failing at CVSS 7.0, and ships the false positives that scan has looked into
in @framework/dependency-check-suppressions.xml@, each with its reason. To
cover @framework/lib/@ in your application's own dependency-check, add the
directory to its scan and that file to its suppressions:

bc. plugins {
    id("org.playframework.play1")
    id("org.owasp.dependencycheck") version "12.2.2"
}

play1 {
    frameworkPath.set(file("/opt/play1"))
}

dependencyCheck {
    val framework = play1.frameworkPath.get().dir("framework").asFile
    setScanSet(listOf(framework.resolve("lib")))
    suppressionFiles = listOf(framework.resolve("dependency-check-suppressions.xml").path)
}

The @dependencyCheck@ block has to come after the @play1@ block that sets
@frameworkPath@. The plugin reads @suppressionFile@ and @suppressionFiles@
together, so a suppressions file of your own stays where it is.

Two traps:

* Use @setScanSet(...)@. In dependency-check-gradle 12.2.2 only that setter marks the scan set as configured. With @scanSet.from(...)@ or a Kotlin @scanSet = ...@ the set stays unconfigured, and the plugin scans its defaults (@src/main/resources@, @package.json@ and so on) instead, without a word about @framework/lib@.
* A jar scanned from a directory has a package URL only when it carries Maven metadata of its own, and many, Micrometer's among them, do not. A suppression that names one by @packageUrl@ can therefore match nothing, without a warning. Match it by @filePath@, as the shipped file does:

bc. <suppress>
    <notes>Why this finding does not apply.</notes>
    <filePath regex="true">.*[/\\]framework[/\\]lib[/\\]some-library-[^/\\]*\.jar$</filePath>
    <cve>CVE-2026-12345</cve>
</suppress>

A finding in @framework/lib/@ that is not a false positive is the
framework's to fix. Until a release carries the fix, @appManagedLibraries@
(above) lets your application take the library over at a fixed version. The
framework's jar then stays in @framework/lib/@ but off your classpaths, so
your scan still reports it: suppress that finding by @filePath@ in your own
file, saying why.


h2. <a name="resolving">Resolving dependencies</a>

Gradle resolves dependencies the first time you run any @play@ command
(@play run@, @play test@, etc.) and re-resolves whenever @build.gradle.kts@
changes. To inspect the resolved classpath:

bc. play classpath

To list resolved dependencies in tree form:

bc. ./gradlew dependencies

To force a re-resolve (e.g. after editing @build.gradle.kts@):

bc. ./gradlew --refresh-dependencies <task>


h2. <a name="framework">Framework dependencies</a>

The framework's own build (under @framework/@) still uses Apache Ivy with a
declarative manifest at @framework/dependencies.yml@. This is internal: Play 1
fork maintainers run @ant resolve@ to update @framework/lib/@. Application
authors never touch this file.
