h1. Deployment options

Play 1.12 applications are deployed as **standalone JVM processes** running an embedded Netty server. There is no servlet-container path: the marquee features of this fork — HTTP/2 ALPN, HTTP/3 over QUIC, virtual-thread dispatch — are Netty-exclusive by design.

For the embedded HTTP server's capabilities — HTTP/2, HTTP/3, virtual threads, TLS — see the "HTTP server":httpserver section.

This page covers the two supported deployment topologies: running Play directly, and running it behind a reverse proxy.

h2. <a name="standalone">Standalone Play applications</a>

The simplest deployment is to run Play directly. The embedded Netty server handles thousands of concurrent connections per CPU core, supports long polling, server-sent events, WebSockets, and direct streaming of @File@ and @InputStream@ bodies — without blocking the request thread. Virtual threads (always on in this fork) make blocking I/O calls inside controllers cheap.

Please refer to the "'Put your application in production' page":production for a full pre-flight checklist (logging, secrets, JPA configuration, JVM flags).

h3. Starting and stopping

Start the application in the background:

bc. play start /path/to/myapp

This forks a JVM, redirects stdout and stderr to @logs/system.out@, writes the PID to @server.pid@, and returns. The framework boots in @prod@ mode by default; pass @--%<id>@ to choose a different framework ID (e.g. @--%staging@).

Stop a running instance with:

bc. play stop /path/to/myapp

That reads @server.pid@ and sends a clean shutdown signal so in-flight requests drain.

To restart without dropping the running instance entirely (useful after a config change), call @play stop@ then @play start@ in sequence; for production zero-downtime swaps, run two instances behind a reverse proxy (next section) and rotate them.

h3. Tailing the logs

Once started, tail @logs/system.out@ for stdout/stderr from the JVM and @logs/application.log@ for the framework's log4j2 output:

bc. tail -F /path/to/myapp/logs/system.out
tail -F /path/to/myapp/logs/application.log

If you've enabled JSON logging (@application.log.format=json@), the application log is line-delimited JSON suitable for ingestion by Loki, Elasticsearch, Datadog, etc. See "Structured JSON logging":logs#json.

h3. JVM tuning

Pass JVM flags to @play start@ via the JVM options syntax — @play@ forwards anything matching @-X@ / @-D@ / @-XX:@:

bc. play start /path/to/myapp -Xms2g -Xmx2g -XX:MaxRAMPercentage=75

Virtual threads make per-request stack memory negligible, so the historical "tune @play.pool@ to match cores" guidance no longer applies — those keys are gone in 1.12 (see the boot @WARN@ if your config still references them).

h3. <a name="conf-jvm">JVM settings in application.conf</a>

JVM flags can also live in @application.conf@, where they apply however the application is launched: @play run@, @play start@, @play test@ and the launcher inside a @play bundle@ all read the same keys. A key prefixed with the framework ID, such as @%prod.jvm.memory@, beats the bare key. Flags given on the command line come after these, so the command line wins where a flag is repeated.

* @jvm.memory@ — JVM flags separated by whitespace. Despite the name it takes any flag, not only heap sizes: @jvm.memory=-Xms512m -Xmx2g --add-modules=jdk.incubator.vector@
* @javaagent.path@ — a Java agent jar, passed as @-javaagent:<path>@
* @agentlib@ — a native agent, passed as @-agentlib:<value>@
* @jmx.port@ and @jmx.hostname@ — start "the JMX agent":deployment#jmx on that address. Both are required; one alone does nothing.

h3. <a name="jmx">The JMX agent</a>

@jmx.port@ and @jmx.hostname@ start the JMX agent, and it requires a login and TLS (PF-183). Name the files that hold the users and the keystore settings:

bc. jmx.port=9010
jmx.hostname=10.0.0.5
jmx.password.file=conf/jmx.password
jmx.access.file=conf/jmx.access
jmx.ssl.config.file=conf/jmx-ssl.properties

* @jmx.password.file@ lists the users, one @name password@ pair per line, and @jmx.access.file@ gives each name @readonly@ or @readwrite@.
* @jmx.ssl.config.file@ names a properties file holding @javax.net.ssl.keyStore@ and @javax.net.ssl.keyStorePassword@. JMX runs over RMI rather than HTTP, so this is TLS and not HTTPS, and it takes a Java keystore (PKCS12 or JKS), not the PEM certificate and key the HTTPS listener uses. The connector and its RMI registry are both encrypted.

Paths are relative to the application directory. The password file and the keystore settings file must be readable by their owner only (@chmod 600@). Without a password file the JVM refuses to start; without keystore settings it starts, but no client can connect to the agent.

Either protection can be turned off, and only the literal value @false@ does it:

bc. jmx.authenticate=false
jmx.ssl=false

With both off the agent accepts connections without a login or encryption, and anyone who can reach the port can control the JVM, so keep that to a loopback address on a development machine. Earlier releases always started the agent that way. An application that sets @jmx.port@ and @jmx.hostname@ therefore has to add the files above, or these two lines, before it will start on this release.

Each key is the JDK's @com.sun.management.jmxremote.<name>@ property under a shorter name, and takes effect only together with @jmx.port@ and @jmx.hostname@. Setting the same properties through @jvm.memory@ does not work, because the agent's own flags follow it and the JVM keeps the last value given.

h3. <a name="bundle-jvm">JVM options for a play bundle</a>

A self-contained @play bundle@ ships its own @play@ launcher, which starts the JVM directly rather than through Gradle. It reads the "application.conf keys above":deployment#conf-jvm and takes further options on its command line:

bc. ./play start --%prod -Xmx2g -ea --add-opens=java.base/java.lang=ALL-UNNAMED

When upgrading, note that bundle launchers before PF-183 ignored the @application.conf@ keys. Check the file for JVM settings that will now take effect in production: a heap size written for development, an agent, or @jmx.port@ with @jmx.hostname@, which now start "the JMX agent":deployment#jmx and stop the JVM from starting until its password file is in place.

From the command line it forwards the following to the JVM (PF-183):

* @-X...@, @-XX:...@, @-Xlog:...@ and @-D...@
* @-javaagent:...@ and @-agentlib:...@
* @--add-modules=...@, @--add-opens=...@, @--add-exports=...@, @--add-reads=...@ and @--enable-native-access=...@
* @--enable-preview@
* the assertion switches @-ea@, @-da@, @-enableassertions@ and @-disableassertions@, bare or with a @:...@ suffix, and @-esa@, @-dsa@, @-enablesystemassertions@ and @-disablesystemassertions@

The long options are forwarded only when option and value are joined with @=@: write @--add-opens=java.base/java.lang=ALL-UNNAMED@, not @--add-opens java.base/java.lang=ALL-UNNAMED@. Nothing is dropped silently — every argument the launcher neither consumes itself (@./play help@ lists its own options) nor forwards is named on standard error, one line per argument; standard output and the exit code are unaffected.

The launcher also loads @certs/.env@ into the environment before it starts the JVM; see "The certs/.env file":configuration#dotenv.

h3. <a name="aot-cache">The AOT cache for a play bundle</a>

JDK 25 can record the classes an application loads and links while it starts, keep them in an _AOT cache_, and start from that cache the next time instead of reading, parsing and verifying the same classes again ("JEP 483":https://openjdk.org/jeps/483, "JEP 514":https://openjdk.org/jeps/514). The launcher inside a @play bundle@ creates such a cache and uses it (PF-180). The classes of the application itself, which Play loads from @precompiled/@, come out of the cache as well.

Create the cache once, in the unpacked bundle, on the machine that runs it:

bc. ./play aot-gen

@aot-gen@ is a training run, and it **starts the application for real with its real configuration**: the framework ID, @application.conf@, @certs/.env@ and JVM options that @./play run@ would use. The application connects to its database, applies what it applies at startup, runs its <code>@OnApplicationStart</code> jobs and opens every port it is configured to open. The launcher waits until it listens, requests @GET /@ once and stops it, and the JVM writes the cache as it exits. The result is @app.aot@ in the bundle's root directory; the command prints its path and size, and the application's output during the run is in @logs/aot-gen.out@.

From then on @./play run@ and @./play start@ pass @-XX:AOTCache=app.aot@ to the JVM whenever that file exists. Delete the file to go back.

Give @aot-gen@ the arguments the application is started with, because a cache only fits a JVM started with the same options:

bc. ./play aot-gen --%prod -XX:+UseZGC --add-modules=jdk.incubator.vector
./play start   --%prod -XX:+UseZGC --add-modules=jdk.incubator.vector

Options kept in "application.conf":deployment#conf-jvm reach both commands by themselves, which is the simplest way to keep the two in step.

**The training run**

* It waits on the port given with @--http.port@, else on @http.port@ from @application.conf@, else on 9000, and starts the application with that port. An @http.port@ that is not a plain number, such as a @${...}@ placeholder, cannot be read by the launcher: pass @--http.port@. If @http.address@ is set, that is the address it connects to; otherwise @127.0.0.1@.
* If the port is already in use — because the application is running, for one — @aot-gen@ refuses and starts nothing. Stop the application, or give the training run a free port with @--http.port@.
* It waits 120 seconds for the application to listen; set @PLAY_AOT_TIMEOUT@ to another number of seconds for one that needs longer. Stopping has no limit of its own: the application shuts down as it does for @./play stop@, and the JVM then needs a few seconds to write the cache.
* When the application exits before it listens, does not listen in time or does not answer, or the JVM does not finish writing the cache — the step runs in a process of its own, which a container's memory limit can end — @aot-gen@ says so, shows the last lines of the application's output and exits with status 1. A failed run changes nothing: a cache already in place stays, nothing half-written is left behind, and the pid file of an instance started with @./play start@ is never read or written.
* The launcher uses bash's built-in @/dev/tcp@ for all of this, so it needs neither @curl@ nor @nc@.

**What a cache is tied to**

The JVM checks a cache before it uses it. A cache fits only:

* the **JDK build** that wrote it — another vendor's build or the next update release does not accept it;
* the **garbage collector and the layout of the heap** — a cache trained with the default collector is rejected under ZGC and the other way round, and so is one trained with a different setting of compressed object pointers (a heap above roughly 32 GB turns them off) or of @-XX:+UseCompactObjectHeaders@;
* the **module options**: @--add-modules@, @--enable-native-access@ and Java agents;
* the **exact classpath** — the bundle's jars, by path, size and modification time;
* the **operating system and CPU architecture**.

The simplest rule is to train with exactly the options production runs with. The framework ID and the HTTP port are not on the list: a training run may use an ID of its own whose @application.conf@ entries point at a scratch database, provided the JVM options it resolves are the ones production uses.

It follows that:

* a cache **cannot ship inside the bundle zip**. It is generated on the target host, or in the image build by a step that runs @./play aot-gen@ — and that step starts the application, so it needs whatever the application needs to start;
* it is **generated again** after a JDK update, after a change of JVM options and after every redeploy, since a new bundle brings new jars;
* a cache that no longer fits is **harmless**. The JVM prints a few @[aot]@ warning and error lines when it starts — they end up in @logs/system.out@ — and starts without the cache, at the speed it had before. A class of the application that has changed is never taken from a cache either. A stale cache costs startup time, not correctness.

To see whether the cache is used, start with @-Xlog:aot@, which reports @Opened AOT cache app.aot@. A few @[aot]@ warnings alone do not mean it was rejected: some JDK 25 builds print them at every start for a cache they go on to use, and a rejection also carries @[aot]@ lines at the @error@ level. To make an unusable cache a startup failure rather than a warning, start with @-XX:AOTMode=on@.

**Your own options win**

The launcher puts @-XX:AOTCache=app.aot@ ahead of the options from @application.conf@ and the command line, and the JVM keeps the last value it is given, so @-XX:AOTCache=<another file>@ and @-XX:AOTMode=off@ do what they say. The JVM refuses to start when @-XX:AOTCache@ is combined with @-Xshare:...@, @-XX:SharedArchiveFile@, @-XX:SharedClassListFile@, @-XX:DumpLoadedClassList@, @-XX:AOTCacheOutput@ or @-XX:AOTMode=record@; when one of those is present, or @-XX:AOTMode=create@ or @-XX:AOTConfiguration@, the launcher leaves its own option out.

**Limits**

* **Bundles only.** An application launched through Gradle — @play run@, @play start@, @play test@, and a @play dist@ artifact, which is deployed into that context — has @conf/@ and Gradle's output directories on its classpath, and the JVM does not write a cache while a non-empty directory is on the classpath.
* **Not from Git Bash on Windows.** @aot-gen@ refuses to run from Git Bash, MSYS2 or Cygwin: the JVM writes the cache when it exits normally, and from those shells @kill@ ends a native @java.exe@ at once. @./play run@ and @./play start@ are unaffected, and use an @app.aot@ that is there.

h3. <a name="startup-profile">Where a bundle's startup time goes</a>

Every start logs a "Started in" line that splits its time by phase; "Startup time":production#startup explains each name. The table is that line for one small application, as a guide to what to expect and to what the cache changes. Read your own application's line before tuning anything: the proportions depend on what its plugins do when it starts.

The application is a freshly generated one with one JPA entity on an in-memory H2 database, bundled with @play bundle@ and started with @./play run@. Each figure is the median of five starts, in milliseconds, on JDK 25.0.2 on one macOS arm64 machine. The ZGC columns add @-XX:+UseZGC@ and the incubator vector module, and use a cache trained with the same options.

|_. Phase |_. No cache |_. AOT cache |_. ZGC, no cache |_. ZGC, AOT cache |
| @jvm@ | 65 | 116 | 66 | 50 |
| @conf@ | 41 | 28 | 40 | 39 |
| @logging@ | 165 | 64 | 169 | 101 |
| @plugins@ | 15 | 3 | 15 | 6 |
| @classes@ | 2 | 1 | 2 | 1 |
| @routes@ | 265 | 126 | 270 | 190 |
| @onApplicationStart@ | 650 | 98 | 662 | 219 |
| — of which @JPAPlugin@ | 550 | 79 | 545 | 176 |
| — of which @DBPlugin@ | 67 | 10 | 70 | 21 |
| — of which @MetricsPlugin@ | 34 | 8 | 35 | 21 |
| @bind@ | 77 | 31 | 78 | 41 |
| @other@ | 18 | 17 | 17 | 41 |
| **Started in** | **1,306** | **483** | **1,319** | **689** |
| Launch to the first answered request | 1,767 | 794 | 1,811 | 1,041 |

The last row is measured from outside: from running @./play run@ to the first @200@ on @GET /@. It is longer than the line's total because it also counts the launcher script before the JVM starts and the first request itself.

What the figures say:

* **Most of a start is spent loading libraries, not running the application.** Without a cache, @JPAPlugin@ building the Hibernate entity manager factory is two fifths of the start, and @logging@ (Log4j) and @routes@ (the first use of the Groovy template engine) are another third. That is loading and linking thousands of library classes, which is the work the cache keeps, and why those three phases shrink the most.
* **The cache more than halves the start** with the default collector: 1,306 ms to 483 ms in the log line, 1,767 ms to 794 ms from launch to first answer.
* **Under ZGC the gain is smaller**, 1,319 ms to 689 ms. The JVM can take loaded classes from a cache under ZGC but not the pre-linked form it uses under the default collector. A cache still has to be trained with the collector it will run under.
* **The application's own classes are a small share.** An application of 2,000 classes spends about 80 ms in @classes@, reading them out of "precompiled/classes.jar":#precompiled-jar and defining them, and about 40 ms with the cache. From the tree of class files that a working copy has, the same takes about 160 ms and 105 ms.
* **A large application gains less in proportion and more in absolute time.** One with 2,000 classes, a large JPA model and about fifty start-up jobs went from 3,005 ms to 1,899 ms under ZGC. Two thirds of what was left was @onApplicationStart@ and @afterApplicationStart@.
* **What remains after the cache is the application's own start-up work**: opening the database pool, validating or updating the schema ("jpa.ddl":configuration#jpa.ddl), and whatever its @OnApplicationStart@ jobs do. The @onApplicationStart.<plugin>@ pairs and @afterApplicationStart@ show where to look.

h3. <a name="bundle-classpath">Upgrading: conf/ is no longer on a bundle's classpath</a>

Until PF-180 the JVM classpath of a @play bundle@ began with the @conf/@ directory. It now holds jars only, because of the rule above: no AOT cache while a directory is on the classpath. @conf/@ still ships in the bundle, and everything Play does with it is unchanged:

* @application.conf@ and the files it includes, @routes@, @messages@ and the files @application.conf@ names by path were always read as files;
* the Log4j configuration — the file named by "application.log.path":configuration#application.log.path, or @conf/log4j.xml@ / @conf/log4j.properties@ when that key is unset — is now looked up in @conf/@ by Play itself;
* so is @conf/play.static@;
* @conf/play.plugins@, fixtures, and any resource the application loads through its own classes (@MyController.class.getResource(...)@), through @Play.classloader@, or through the context class loader of a request or job thread still resolve: Play's class loader searches @conf/@ itself. That loader is also in place while Play starts JPA, so @conf/hibernate.properties@ and a "jpa.mapping-file":configuration#jpa.mapping-file are found as before.

What changes is a lookup that goes through the JVM's own class loader, because that loader no longer sees @conf/@:

* @ClassLoader.getSystemResource(...)@ and @ClassLoader.getSystemClassLoader().getResource(...)@;
* a class loaded from a jar — in the application's @lib/@, in a module's @lib/@ or among the framework's libraries — that looks a resource up through itself. This is how many libraries find an optional configuration file by a well-known name. Log4j's @log4j2.component.properties@ is one such file: kept in @conf/@, it is no longer read in a bundle;
* a file placed in @conf/@ to shadow a resource inside the framework jar, such as @play/libs/mime-types.properties@.

For a file a library has to find, put it in a jar in the application's @lib/@ directory before you run @play bundle@ — every jar found there when the bundle is built goes onto its classpath:

bc. jar cf lib/conf-resources.jar -C conf log4j2.component.properties

Make that a step of the build: @lib/@ is in the @.gitignore@ of a new application, and a jar added to the @lib/@ of a bundle that is already unpacked is not used, because the launcher starts the JVM with exactly the jars the bundle's @.classpath@ file lists. Many such files also have a system property that does the same job, which can go in @jvm.memory@.

An application launched through Gradle is not affected: there @conf/@ is still the first classpath entry.

h2. <a name="precompiled">Deploying without source code</a>

When you want to ship only the build artifact — for locked-down servers, lean container images, or distributing a closed-source app to a customer — Play can run from a precompiled bytecode tree alone, with no @app/@ sources on disk. Note that "production mode" (@application.mode=prod@) on its own does not do this: it pre-compiles at boot, but still reads the source tree to do so. The flow below is what lets you omit @app/@ entirely from the deployed artifact.

h3. Step 1 — precompile on the build host

bc. play precompile /path/to/myapp

This compiles every Java class under @app/@ and every Groovy template under @app/views/@ (plus equivalents inside any modules) and writes the bytecode to:

bc. myapp/precompiled/

The directory is regenerated from scratch on each invocation — the command deletes any existing @precompiled/@ and @tmp/@ before running.

h3. Step 2 — assemble the deployment artifact

The runtime needs:

* @precompiled/@ — output from step 1
* @conf/@ — @application.conf@, @routes@, log4j config, messages, keystores
* @lib/@ — runtime dependencies
* @public/@ — static assets

You can omit:

* @app/@ — controllers, models, templates (now living as bytecode under @precompiled/@)
* @test/@ — tests
* @tmp/@ — runtime cache (recreated on boot)
* @build.gradle.kts@, @gradle/@, @.gradle/@ — build-time only

If the host has no @logs/@ directory, the @play@ launcher creates one on first start.

h3. Step 3 — start in precompiled mode

Tell the framework to load from @precompiled/@ instead of recompiling at boot:

bc. play start /path/to/myapp -Dprecompiled=true

The system property forces @prod@ mode and skips both the Java and template compile passes. If @precompiled/@ is missing, the framework logs @"Precompiled classes are missing!!"@ and refuses to start.

h3. <a name="precompiled-jar">The classes in a bundle or dist: precompiled/classes.jar</a>

@play precompile@ writes the classes as a tree of files, @precompiled/java/@, and an application started from its working copy with @-Dprecompiled=true@ runs off that tree. @play bundle@ and @play dist@ pack the tree into one jar as they build the artifact, so a deployed application carries a single @precompiled/classes.jar@ in place of a few thousand class files. The jar is made for the artifact only: nothing is added to the @precompiled/@ of the working copy.

At startup Play reads the jar where the application has one, and the tree otherwise. The jar is not on the JVM's classpath. Play's own class loader takes the classes out of it, exactly as it does from the tree, so nothing else about the application changes. Where both are present — an artifact unpacked over an older installation, say — the jar is used and the tree is ignored. Precompiled templates stay files, under @precompiled/templates/@.

A @.distignore@ entry below @precompiled/java/@ still decides which classes ship: it now keeps them out of the jar.

**Upgrading.** Anything of your own that looks into @precompiled/java/@ of an _installed_ bundle or dist has to look into the jar instead. A jar works wherever a class directory did:

bc. java -cp precompiled/classes.jar utils.SomeTool
unzip -l precompiled/classes.jar

Scripts that work on the tree in the working copy, between @play precompile@ and packaging, need no change.

**Rewriting the classes before they ship.** A build step that processes the classes — ProGuard, to strip debug information or to obfuscate — can do it in either of two ways.

* _On the tree._ A task that rewrites @precompiled/java/@ in place and that @playBundle@ and @playDist@ depend on keeps working unchanged: the jar is packed from whatever the tree holds when the artifact is built.
* _On one jar._ The @playPrecompiledJar@ task packs the tree into @build/play/precompiled/classes.jar@. Run the tool from that jar to another, and hand the result to the packaging tasks through their @precompiledJar@ property; they ship it as it is. ProGuard deflates the entries of the jar it writes, and inflating them costs a little at every start (about 25 ms for 2,000 classes); @-dontcompress@ in its configuration keeps them stored, as they are in the jar Play packs itself.

bc. val classesJar = tasks.named<play.gradle.PlayPrecompiledJarTask>("playPrecompiledJar").flatMap { it.jar }
val processedJar = layout.buildDirectory.file("proguard/classes.jar")
 
val proguardClasses = tasks.register<JavaExec>("proguardClasses") {
    inputs.file(classesJar)          // also makes this task run after playPrecompiledJar
    outputs.file(processedJar)
    classpath = configurations["proguard"]
    mainClass.set("proguard.ProGuard")
    argumentProviders.add(CommandLineArgumentProvider {
        listOf("@conf/proguard.pro",
            "-injars", classesJar.get().asFile.path,
            "-outjars", processedJar.get().asFile.path)
    })
}
 
tasks.withType<play.gradle.PlayBundleTask>().configureEach {
    dependsOn(proguardClasses)
    precompiledJar.set(processedJar)
}
tasks.withType<play.gradle.PlayDistTask>().configureEach {
    dependsOn(proguardClasses)
    precompiledJar.set(processedJar)
}

h3. Caveats

* @application.mode=dev@ is incompatible with this layout — hot reload requires source files. The @-Dprecompiled=true@ flag implies @prod@ mode regardless of @application.conf@.
* Stack traces reference bytecode line numbers, not source lines. Keep a copy of the matching sources somewhere off the deployment host for debugging.

h2. <a name="reverseproxy">Behind a reverse proxy</a>

For production deployments, most operators front Play with a reverse proxy that handles TLS termination, virtual hosting, request routing, and (optionally) static-asset caching. Common choices:

* "nginx":https://nginx.org/ — most popular self-hosted choice; supports HTTP/2 and HTTP/3 to the client, plus HTTP/1.1 or HTTP/2 to the upstream.
* "HAProxy":https://www.haproxy.org/ — preferred when L4 load balancing or sticky sessions are needed.
* "AWS Application Load Balancer":https://aws.amazon.com/elasticloadbalancing/application-load-balancer/ — terminates TLS and HTTP/2; does **not** forward UDP, so HTTP/3 from clients ends at the ALB and Play sees TCP only.
* "AWS Network Load Balancer":https://aws.amazon.com/elasticloadbalancing/network-load-balancer/ — passes UDP through, so end-to-end HTTP/3 to Play works (TLS terminates at Play).
* "Cloudflare":https://www.cloudflare.com/ — terminates TLS, HTTP/2, and HTTP/3 at the edge; speaks HTTP/1.1 or HTTP/2 to the origin.

h3. TLS termination

You have two patterns. Pick whichever matches your operational model:

**Pattern A — TLS at the edge, plain HTTP to Play.** The proxy holds the cert; Play binds @http.port@ only, no @https.port@. This is the simplest setup when the proxy is on the same private network. Tell Play the canonical scheme and host so reverse routing emits the right URLs:

bc. http.port=9000
XForwardedSupport=127.0.0.1
XForwardedProto=https

**Pattern B — TLS at Play.** Play handles TLS itself, including HTTP/2 ALPN and HTTP/3 QUIC negotiation. The proxy can pass through TCP+UDP transparently (NLB / HAProxy in TCP mode) or speak HTTPS to the origin. Bind both @https.port@ and a PEM cert+key:

bc. https.port=9443
certificate.file=/etc/letsencrypt/live/example.com/fullchain.pem
certificate.key.file=/etc/letsencrypt/live/example.com/privkey.pem

See "HTTP server":httpserver for the full TLS configuration reference, and "Default security headers":security#headers for HSTS settings.

h3. Path-prefix rewriting

If the proxy mounts your app under a subpath (e.g. @example.com/myapp@), tell Play so reverse routing emits the right URLs:

bc. http.path=/myapp

The framework prefixes all generated URLs with this value but does **not** strip it from incoming requests — the proxy is responsible for forwarding the full path.

h3. nginx example

A minimal nginx upstream config terminating TLS at the edge and proxying plain HTTP to Play on @127.0.0.1:9000@:

bc. server {
    listen 443 ssl http2;
    server_name example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    location / {
        proxy_pass         http://127.0.0.1:9000;
        proxy_http_version 1.1;
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_read_timeout 600s;
    }
}

Add @application.conf@:

bc. http.port=9000
XForwardedSupport=127.0.0.1
XForwardedProto=https

For HTTP/3 client support without end-to-end QUIC, enable @listen 443 quic@ in nginx and let nginx emit @Alt-Svc@ on its own.

h3. WebSockets through the proxy

WebSockets need an explicit @Upgrade@ / @Connection@ pass-through. With nginx:

bc. location /ws/ {
    proxy_pass         http://127.0.0.1:9000;
    proxy_http_version 1.1;
    proxy_set_header   Upgrade    $http_upgrade;
    proxy_set_header   Connection "upgrade";
    proxy_read_timeout 86400s;
}

Server-sent events also work over standard @proxy_pass@, but make sure response buffering is off:

bc. proxy_buffering off;

h3. Serving the Nuxt frontend

An application scaffolded with @play new <name> --frontend@ keeps its Nuxt sources in @frontend/@. The @playFrontendSpa@ task — which both @play dist@ and @play bundle@ depend on — runs @pnpm install@ and @pnpm run generate@, then copies @frontend/.output/public@ into @public/spa/@, so the built SPA travels inside the production artifact.

Nuxt generates that build for the **site root**: the emitted markup references its assets as @/_nuxt/...@. Serve @public/spa/@ at @/@ and proxy only the API paths through to Play:

bc. location / {
    root      /var/www/myapp/public/spa;
    try_files $uri $uri/ /index.html;
}

location /api/ {
    proxy_pass         http://127.0.0.1:9000;
    proxy_http_version 1.1;
    proxy_set_header   Host              $host;
    proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
    proxy_set_header   X-Forwarded-Proto $scheme;
}

The @try_files ... /index.html@ fallback is what makes client-side routing work: a deep link such as @/settings/profile@ has no file behind it and must still be answered with the SPA shell, so the router can take over in the browser.

Play's @staticDir:public@ route also serves these same files, at @/public/spa/...@, but that URL is not usable as-is — the generated markup asks for its assets at the root, so the page itself loads while every script and stylesheet 404s. If you would rather serve the SPA from Play than from the proxy, generate it with a matching base path so the two agree:

bc. NUXT_APP_BASE_URL=/public/spa/ pnpm run generate

and reach it at @/public/spa/@.

h3. Heroku and other PaaS

PaaS platforms generally just need the app to honor a @PORT@ environment variable. Read it in @application.conf@:

bc. http.port=${PORT}

The platform handles TLS at the edge. See the "VPS / Custom Server":#upstart section below for a generic process-supervisor pattern.

h2. <a name="upstart">Running as a system service</a>

For a long-running process on a Linux server, use systemd, an init script, or a process supervisor. Example systemd unit:

bc. [Unit]
Description=Play Framework — myapp
After=network.target

[Service]
Type=forking
User=play
Group=play
WorkingDirectory=/srv/myapp
PIDFile=/srv/myapp/server.pid
ExecStart=/opt/playframework/play start /srv/myapp --%prod
ExecStop=/opt/playframework/play stop /srv/myapp
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target

Then:

bc. systemctl daemon-reload
systemctl enable myapp
systemctl start myapp
journalctl -u myapp -f
