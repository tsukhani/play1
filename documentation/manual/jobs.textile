h1. Asynchronous Jobs

Because Play is a web application framework, most of the application logic is done by controllers responding to HTTP requests. 

But sometimes you will need to execute some application logic outside of any HTTP request. It can be useful for initialization tasks, maintenance tasks or to run long tasks without blocking the HTTP request execution pool.

Jobs are fully managed by the framework. That means that Play will manage all the database connection stuff, JPA entity manager synchronization and transactions management for you. To create a job you just need to extend the @play.jobs.Job@ super class.

p(note). **Virtual threads.** Job execution runs on "virtual threads":https://openjdk.org/jeps/491. There is no fixed job pool size to tune — the framework dispatches each scheduled or triggered job on its own virtual thread; only timer dispatch uses the two-thread platform pool. The legacy @play.jobs.pool@ key is gone, along with @play.threads.virtual*@; @Play.java@ emits a WARN at boot if any of those keys are still present in @application.conf@.

bc. package jobs;
 
import play.jobs.*;
 
public class MyJob extends Job {
    
    public void doJob() {
        // execute some application logic here ...
    }
    
}

Sometimes you need to create jobs that return a result. You then override the @doJobWithResult()@ method.

bc. package jobs;
 
import play.jobs.*;
  
public class MyJob extends Job<String> {
    
    public String doJobWithResult() {
        // execute some application logic here ...
        return result;
    }
    
}

Here the use of @String@ is just for the example, of course a job can return any object type.

h2. <a name="concepts">Bootstrap jobs</a>

Bootstrap jobs are executed by Play at application start time. To mark your job as a bootstrap job you just need to add the <code>@OnApplicationStart</code> annotation.

bc. import play.jobs.*;
 
@OnApplicationStart
public class Bootstrap extends Job {
    
    public void doJob() {
        if(Page.count() == 0) {
            new Page("root").save();
            Logger.info("A root page has been created.");
        }
    }
    
}

You don’t need to return a result. Even if you do it, the result will be lost.

The default is that all jobs annotated with <code>@OnApplicationStart</code> will be executed in sequence. When all jobs are finished, your application is ready to start processing incoming requests.

You can control the order of synchronous bootstrap jobs with the <code>priority</code> element: lower values run first (0 is the highest priority and the default), matching the <code>@Before</code>/<code>@After</code> interceptor convention. Jobs with the same priority keep their natural order. This is handy when one job must complete before another — for example applying a schema migration before warming a cache:

bc. @OnApplicationStart(priority = 0)
public class MigrateSchema extends Job { ... }

@OnApplicationStart(priority = 10)
public class WarmCaches extends Job { ... }

If you want your jobs to start when your application starts, but you want to start processing incoming requests immediately, you can annotate your job like this: <code>@OnApplicationStart(async=true)</code>. Then your job will be started in the background when the application starts. All async jobs will be started at the same time. <code>priority</code> only orders the synchronous jobs; async jobs are submitted in priority order but, running concurrently, may still finish in any order.

p(note). **Warning**
 
When you run the application in DEV mode, the application waits for the first HTTP request to start. Moreover when you are in DEV mode, the application will sometimes automatically restart when needed. 
 
When you run in PROD mode, the application will start synchronously with the server start.

h2. <a name="scheduling">Scheduled jobs</a>

Scheduled jobs are run periodically by the framework. You can ask Play to run a job at a specific interval using the <code>@Every</code> annotation.

bc. import play.jobs.*;
 
@Every("1h")
public class Bootstrap extends Job {
    
    public void doJob() {
        List<User> newUsers = User.find("newAccount = true").fetch();
        for(User user : newUsers) {
            Notifier.sayWelcome(user);
        }
    }
    
}

The above annotation is for hours, if you want to specify the time duration in minutes or seconds, you can do it in the following way:-
i) For Minutes - @Every("3mn"),@Every("30mn")
ii) For Seconds - @Every("35s"),@Every("56s")

If the <code>@Every</code> annotation is not enough you can use the <code>@On</code> annotation to run your jobs using a CRON expression.

bc. import play.jobs.*;
 
/** Fire at 12pm (noon) every day **/ 
@On("0 0 12 * * ?")
public class Bootstrap extends Job {
    
    public void doJob() {
        Logger.info("Maintenance job ...");
        ...
    }
    
}

p(note). **Tip**
 
We use the CRON expression parser from the "Quartz library":http://www.quartz-scheduler.org/docs/tutorials/crontrigger.html.

You don’t need to return a result. Even if you do it, the result will be lost.

h2. <a name="tasks">Triggering task jobs</a>

You can also trigger a Job at any time to perform a specific task by simply calling @now()@ on a Job instance. Then this job will be run immediately in a non blocking way. 

bc. public static void encodeVideo(Long videoId) {
    new VideoEncoder(videoId).now();
    renderText("Encoding started");
}

Calling @now()@ on a Job returns a @Promise@ value that you can use to retrieve the task result once finished, or an exception if something went wrong with task execution.

If you want to schedule a Job to run after some delay, @in(int seconds)@ method is there to help you. Calling @in(0)@ has the same effect as @now()@.

Sometimes when dealing with http requests you want to schedule a Job to run after request is responded. A natural use case would be if you create and save new JPA entities and the Job has to retrieve them from database by some identifier and process them. Triggering a Job with @now()@ won't work, because transaction is not yet committed, so a thread executing the task won't be able to retrieve entities; @in(delay)@ will work, but it is not flexible enough. For those cases @Job@ offers @afterRequest()@ method that will schedule a job to run when request is served.
If @afterRequest()@ is called not from http invocation context, it behaves like @now()@.

All @now()@, @in()@, @afterRequest()@ return a @Promise@ so you have access to this Job execution result.

h2. <a name="concepts">Stopping the application</a>

Because you sometimes need to perform some action before the application shutdown, Play also provides a <code>@OnApplicationStop</code> annotation.

bc. import play.jobs.*;
 
@OnApplicationStop
public class Bootstrap extends Job {
 
    public void doJob() {
        Fixture.deleteAll();
    }
}

h2. <a name="context">Context propagation</a>

A request, a job and a task you hand to an executor each run on a thread of their own, and what Play keeps per thread does not follow the work from one thread to the next. Two things are carried along for you:

|_. Carried |_. What it is |
| The logging context | The Log4j @ThreadContext@ map. For a request that is its "per-request fields":logs#json-mdc, @request_id@ among them, plus any key your own code has put there |
| The language | What @Lang@ holds for the thread that starts the work |

A job that an action starts with @now()@, @in()@ or @afterRequest()@ runs with both, as they were when that method was called. Its log lines carry the @request_id@ of the request that started it, so one search finds the request and everything it set off (the lines are abridged):

bc. {"@timestamp":"2026-10-09T05:03:45.051Z","log.level":"INFO","message":"Encoding requested","process.thread.name":"play-vthread-3","action_name":"Videos.encode","http_path":"/videos/42/encode","request_id":"d65c92c2-e71c-43f5-9372-a16731b77990"}
{"@timestamp":"2026-10-09T05:03:45.052Z","log.level":"INFO","message":"Encoding video 42","process.thread.name":"jobs-vthread-3","action_name":"Videos.encode","http_path":"/videos/42/encode","jobId":"8d546897-b911-490a-8dfa-617ac7cabdd9","request_id":"d65c92c2-e71c-43f5-9372-a16731b77990"}

This is also true of a job started with @afterRequest()@ or @in()@, which runs when the request is over and its own logging context is gone.

A request resolves its language the first time something asks for it: a template, @Messages.get()@ or @Lang.get()@. An action that starts a job before any of those has run, and wants the job to work in the request's language, calls @Lang.get()@ first.

Bootstrap jobs and scheduled jobs (<code>@Every</code>, <code>@On</code>, @every()@) have no request behind them, so they carry no request keys.

h3. The job id

Every run of every job, however it was started, logs under a @jobId@. It is a random UUID, like @request_id@, made when the run starts. It stays the same for the whole run and differs from one run to the next, also between two runs of the same job that overlap, so the lines of one run can be told apart from all others. A job started from another job gets a @jobId@ of its own and inherits the rest.

In @text@ mode, add @%X{jobId}@ to the log pattern to see it.

h3. What is not carried

The request, the response, the session, the flash scope, the params, the render and route arguments, the validation errors, the JPA entity manager and the database connection all stay with the request. They change while the request runs and are not safe to use from two threads, so they are never handed to another thread: in a job started with @now()@, @in()@ or @afterRequest()@, @Request.current()@ is @null@, and the job has a transaction and an entity manager of its own, as it always had. An entity loaded by the request does not belong to the job's entity manager either.

Hand a job what it needs through its constructor, as values and identifiers:

bc. public static void encode(Long videoId) {
    new VideoEncoder(videoId, session.get("user")).now();
    renderText("Encoding started");
}

h3. Threads of your own

A task you run on an executor of your own is not a job, and gets no context unless you wrap it with @play.utils.ContextPropagator@:

bc. Future<Quote> quote = executor.submit(ContextPropagator.wrap(() -> quotes.fetch(symbol)));

@wrap()@ takes a @Runnable@ or a @Callable@ and records the context of the thread that calls it. The task then runs with exactly that context, in place of whatever the executor's thread held, and when it ends, also by throwing, that thread gets back what it held before. So a wrapped task can itself wrap and start further tasks, and tasks forked side by side do not see each other's changes.

The framework wraps nothing else for you: mail sent in the background and the threads that complete asynchronous @WS@ calls log without the context.

h3. Carrying a value of your own

To have a value of your own carried in the same way, register a @play.utils.ThreadLocalAccessor@ for it, typically from a plugin's @onApplicationStart()@:

bc. ContextPropagator.register(new ThreadLocalAccessor<String>() {
    public String key() { return "tenant"; }
    public String capture() { return Tenant.current.get(); }
    public void restore(String tenant) { Tenant.current.set(tenant); }
    public void reset() { Tenant.current.remove(); }
});

@capture()@ runs on the thread that starts the work, and again on the thread that does the work, to record what that thread gets back afterwards. It must not change anything on either, and returns @null@ on a thread that has no value. @restore()@ and @reset()@ run on the thread that does the work, to set the value and to clear it. Registering a second accessor under the same key replaces the first.

Only do this for a value that is safe on two threads at once: an immutable one, or a copy made in @capture()@.
