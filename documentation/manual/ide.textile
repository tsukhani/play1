h1. Setting-up your preferred IDE

Working with Play is easy. You don’t even need a sophisticated IDE as Play compiles and refreshes the modifications you make to your source files automatically. So you can easily work using a simple text editor.

However, using a modern Java IDE provides cool productivity features like auto-completion, on-the-fly compilation, assisted refactoring and debugging. Play has dedicated support for "IntelliJ IDEA":http://www.jetbrains.com/idea/index.html.


h2(#intellij). <a>IntelliJ IDEA</a>

Open the application's @build.gradle.kts@ as a project. IntelliJ's Gradle import
indexes @app/@, @conf/@, @test/@, and each @modules/*/app/@ as source roots
automatically — there is no @idealize@ step.

# On the command line, run @play new myApp@ to scaffold a new application.
# In IntelliJ IDEA, *File → Open* and select the generated @build.gradle.kts@.
# Confirm the Gradle import dialog. The Play 1 plugin pins a Java 25 toolchain.

To run the app from IntelliJ, use the Gradle tool window and double-click the
@play1 → playRun@ task. The same panel exposes @playTest@, @playAutotest@,
@playPrecompile@, and the rest of the @play1@ task group.


h2(#custom). <a>Other IDEs and editors</a>

Any editor that understands Gradle (VS Code with the Gradle for Java extension, NetBeans, Eclipse with Buildship) can import @build.gradle.kts@ the same way IntelliJ does — classpath, source roots, the Java 25 toolchain, and the @play1@ task group all come from the Gradle model. There is no manual @PLAY_PATH@/@play.jar@/@-javaagent@ wiring to do; the @playRun@ task assembles all of that internally.

For light-touch editors (Vim, Emacs, plain Sublime), let Gradle drive the build from a terminal:

bc. ./gradlew :playRun                   # dev mode, hot reload
./gradlew :playTest                       # interactive test runner
./gradlew :playPrecompile                 # PROD-mode precompile

Run @./gradlew tasks --group play1@ from inside an app to see the full set.


h2. <a>Debugging issues</a>

Play automatically reloads Java classes when the Java sources are modified. However as Java does not fully support class reloading, the JDPA debugger can easily get confused: breakpoint submission may fail or the debugger may stop on the wrong line when you step into the code.

To avoid this behavior, a better way is to start a fresh debugging session after a code modification. Luckily, JPDA supports the ability to connect and disconnect the debugger at any time without restarting the JVM.

So the correct workflow for debugging is:

# <span>Make changes to your source code.</span>
# <span>Refresh the browser to see the results. (At this time Play will reload your code modifications and redefine classes in the JVM.)</span>
# <span>If something goes wrong and you need to debug, start a new debug session.</span>
# <span>Debug and correct your code.</span>
# <span>Disconnect the debugger.</span>

By using this work-flow you will always have a debugger synchronized with the code loaded in the JVM.
