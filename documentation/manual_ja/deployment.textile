h1. デプロイオプション

Play 1.12 アプリケーションは、組み込み Netty サーバを実行する **スタンドアロンの JVM プロセス** としてデプロイされます。サーブレットコンテナ経由のパスはありません: このフォークの主要機能 — HTTP/2 ALPN、HTTP/3 over QUIC、仮想スレッドディスパッチ — は設計上 Netty 専用です。

組み込み HTTP サーバの機能 (HTTP/2、HTTP/3、仮想スレッド、TLS) については "HTTP サーバ":httpserver を参照してください。

このページでは、サポートされている 2 つのデプロイトポロジ — Play を直接実行する方法と、リバースプロキシの背後で実行する方法 — について説明します。

h2. <a name="standalone">スタンドアロン Play アプリケーション</a>

最もシンプルなデプロイは Play を直接実行することです。組み込み Netty サーバは CPU コアあたり数千の同時接続を捌くことができ、ロングポーリング、Server-Sent Events、WebSocket、@File@ や @InputStream@ ボディの直接ストリーミングをサポートします — リクエストスレッドをブロックすることなく。仮想スレッド (このフォークでは常に有効) によって、コントローラ内のブロッキング I/O 呼び出しが安価になります。

事前確認チェックリスト (ロギング、シークレット、JPA 設定、JVM フラグ) の全体については "「アプリケーションを本番環境に投入する」ページ":production を参照してください。

h3. 起動と停止

アプリケーションをバックグラウンドで起動するには:

bc. play start /path/to/myapp

これは JVM をフォークし、stdout と stderr を @logs/system.out@ にリダイレクトし、PID を @server.pid@ に書き込んで戻ります。フレームワークはデフォルトで @prod@ モードで起動します; 別のフレームワーク ID を選択するには @--%<id>@ を渡します (例: @--%staging@)。

実行中のインスタンスを停止するには:

bc. play stop /path/to/myapp

これは @server.pid@ を読み取り、クリーンなシャットダウンシグナルを送信して、処理中のリクエストが完了するのを待ちます。

実行中のインスタンスを完全に落とすことなく再起動するには (設定変更後などに便利)、@play stop@ の後に @play start@ を順に実行します; 本番環境でのゼロダウンタイム切り替えは、リバースプロキシ (次のセクション) の背後で 2 つのインスタンスを実行し、ローテーションさせる方法を使います。

h3. ログの監視

起動後は @logs/system.out@ で JVM の stdout/stderr を、@logs/application.log@ でフレームワークの log4j2 出力を tail します:

bc. tail -F /path/to/myapp/logs/system.out
tail -F /path/to/myapp/logs/application.log

JSON ロギング (@application.log.format=json@) を有効にしている場合、アプリケーションログは行区切りの JSON となり、Loki、Elasticsearch、Datadog などへの取り込みに適します。"構造化 JSON ロギング":logs#json を参照してください。

h3. JVM チューニング

JVM フラグを @play start@ に渡すには JVM オプション構文を使用します — @play@ は @-X@ / @-D@ / @-XX:@ にマッチするすべての引数を転送します:

bc. play start /path/to/myapp -Xms2g -Xmx2g -XX:MaxRAMPercentage=75

仮想スレッドによってリクエストごとのスタックメモリは無視できる程度になるため、従来の「@play.pool@ をコア数に合わせて調整する」というガイダンスはもはや当てはまりません — これらのキーは 1.12 で削除されています (設定にまだ参照が残っている場合は起動時の @WARN@ を確認してください)。

h2. <a name="precompiled">ソースコードなしでのデプロイ</a>

ビルド成果物のみを配布したい場合 — 制限付きサーバ、軽量なコンテナイメージ、クローズドソースアプリケーションを顧客に配布する場合など — Play は @app/@ ソースをディスク上に置かずに、プリコンパイル済みのバイトコードツリーのみで動作できます。注意点として、「本番モード」(@application.mode=prod@) 単体ではこれを行いません: 起動時にプリコンパイルしますが、それでもソースツリーを読み込んで行います。デプロイ成果物から @app/@ を完全に省略できるようにするのが、以下のフローです。

h3. ステップ 1 — ビルドホストでプリコンパイル

bc. play precompile /path/to/myapp

これは @app/@ 配下の全 Java クラスと @app/views/@ 配下の全 Groovy テンプレート (および各モジュール内の同等物) をコンパイルし、バイトコードを以下に書き出します:

bc. myapp/precompiled/

このディレクトリは呼び出しのたびにゼロから再生成されます — コマンドは実行前に既存の @precompiled/@ と @tmp/@ を削除します。

h3. ステップ 2 — デプロイ成果物を組み立てる

ランタイムには以下が必要です:

* @precompiled/@ — ステップ 1 の出力
* @conf/@ — @application.conf@、@routes@、log4j 設定、メッセージ、キーストア
* @lib/@ — ランタイム依存関係
* @public/@ — 静的アセット

以下は省略可能です:

* @app/@ — コントローラ、モデル、テンプレート (@precompiled/@ 配下にバイトコードとして存在)
* @test/@ — テスト
* @tmp/@ — ランタイムキャッシュ (起動時に再作成)
* @build.gradle.kts@、@gradle/@、@.gradle/@ — ビルド時専用

ホストに @logs/@ ディレクトリがない場合、@play@ ランチャが初回起動時に作成します。

h3. ステップ 3 — プリコンパイルモードで起動

起動時の再コンパイルではなく @precompiled/@ からロードするようフレームワークに指示します:

bc. play start /path/to/myapp -Dprecompiled=true

このシステムプロパティは @prod@ モードを強制し、Java とテンプレートの両方のコンパイルパスをスキップします。@precompiled/@ が見つからない場合、フレームワークは @"Precompiled classes are missing!!"@ をログに出力し、起動を拒否します。

h3. 注意点

* @application.mode=dev@ はこのレイアウトと互換性がありません — ホットリロードはソースファイルを必要とします。@-Dprecompiled=true@ フラグは @application.conf@ の設定に関わらず @prod@ モードを強制します。
* スタックトレースはソース行ではなくバイトコードの行番号を参照します。デバッグのために、対応するソースのコピーをデプロイホスト外のどこかに保管しておいてください。

h2. <a name="reverseproxy">リバースプロキシの背後</a>

本番デプロイでは、ほとんどの運用者は TLS 終端、バーチャルホスト、リクエストルーティング、(オプションで) 静的アセットキャッシュを処理するリバースプロキシを Play の前段に置きます。一般的な選択肢:

* "nginx":https://nginx.org/ — 最も人気のあるセルフホスト型の選択肢; クライアントとの間で HTTP/2 と HTTP/3 をサポートし、アップストリームとは HTTP/1.1 または HTTP/2 で通信します。
* "HAProxy":https://www.haproxy.org/ — L4 ロードバランシングや sticky session が必要な場合に推奨。
* "AWS Application Load Balancer":https://aws.amazon.com/elasticloadbalancing/application-load-balancer/ — TLS と HTTP/2 を終端しますが、UDP は転送 **しません** ので、クライアントからの HTTP/3 は ALB で終端し、Play は TCP のみを受信します。
* "AWS Network Load Balancer":https://aws.amazon.com/elasticloadbalancing/network-load-balancer/ — UDP をパススルーするので、Play へのエンドツーエンド HTTP/3 が動作します (TLS は Play で終端)。
* "Cloudflare":https://www.cloudflare.com/ — TLS、HTTP/2、HTTP/3 をエッジで終端し、オリジンとは HTTP/1.1 または HTTP/2 で通信します。

h3. TLS 終端

2 つのパターンがあります。運用モデルに合った方を選んでください:

**パターン A — エッジで TLS、Play へはプレーン HTTP。** プロキシが証明書を保持し、Play は @http.port@ のみをバインドして @https.port@ は使用しません。プロキシが同じプライベートネットワーク上にある場合、これが最もシンプルなセットアップです。リバースルーティングが正しい URL を生成するように、正規スキームとホストを Play に伝えます:

bc. http.port=9000
XForwardedSupport=127.0.0.1
XForwardedProto=https

**パターン B — Play で TLS。** Play 自身が TLS を処理し、HTTP/2 ALPN と HTTP/3 QUIC ネゴシエーションも含めて担当します。プロキシは TCP+UDP を透過的にパススルーすることも (TCP モードの NLB / HAProxy)、オリジンと HTTPS で通信することもできます。@https.port@ と PEM 証明書 + 鍵の両方をバインドします:

bc. https.port=9443
certificate.file=/etc/letsencrypt/live/example.com/fullchain.pem
certificate.key.file=/etc/letsencrypt/live/example.com/privkey.pem

完全な TLS 設定リファレンスは "HTTP サーバ":httpserver を、HSTS 設定は "デフォルトのセキュリティヘッダ":security#headers を参照してください。

h3. パスプレフィックスの書き換え

プロキシがアプリをサブパス (例: @example.com/myapp@) にマウントしている場合、リバースルーティングが正しい URL を生成するように Play に伝えます:

bc. http.path=/myapp

フレームワークは生成されるすべての URL にこの値をプレフィックスしますが、受信リクエストからこれを取り除く処理は **しません** — プロキシ側でフルパスを転送する責任があります。

h3. nginx の例

エッジで TLS を終端し、@127.0.0.1:9000@ の Play にプレーン HTTP でプロキシする最小限の nginx アップストリーム設定:

bc. server {
    listen 443 ssl http2;
    server_name example.com;

    ssl_certificate     /etc/letsencrypt/live/example.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/example.com/privkey.pem;

    location / {
        proxy_pass         http://127.0.0.1:9000;
        proxy_http_version 1.1;
        proxy_set_header   Host              $host;
        proxy_set_header   X-Real-IP         $remote_addr;
        proxy_set_header   X-Forwarded-For   $proxy_add_x_forwarded_for;
        proxy_set_header   X-Forwarded-Proto $scheme;
        proxy_read_timeout 600s;
    }
}

@application.conf@ には以下を追加します:

bc. http.port=9000
XForwardedSupport=127.0.0.1
XForwardedProto=https

エンドツーエンドの QUIC を使わずにクライアントの HTTP/3 サポートを有効にするには、nginx で @listen 443 quic@ を有効にし、nginx 自身が @Alt-Svc@ を発行するようにします。

h3. プロキシ経由の WebSocket

WebSocket には明示的な @Upgrade@ / @Connection@ のパススルーが必要です。nginx の場合:

bc. location /ws/ {
    proxy_pass         http://127.0.0.1:9000;
    proxy_http_version 1.1;
    proxy_set_header   Upgrade    $http_upgrade;
    proxy_set_header   Connection "upgrade";
    proxy_read_timeout 86400s;
}

Server-Sent Events も標準の @proxy_pass@ で動作しますが、レスポンスバッファリングをオフにする必要があります:

bc. proxy_buffering off;

h3. Heroku などの PaaS

PaaS プラットフォームは一般に、アプリが @PORT@ 環境変数を尊重することを要求します。@application.conf@ で以下のように読み取ります:

bc. http.port=${PORT}

プラットフォームがエッジで TLS を処理します。汎用的なプロセス監視パターンについては、後述の "VPS / カスタムサーバ":#upstart セクションを参照してください。

h2. <a name="upstart">システムサービスとしての実行</a>

Linux サーバ上で長時間稼働するプロセスを動かすには、systemd、init スクリプト、またはプロセススーパバイザを使用します。systemd ユニットの例:

bc. [Unit]
Description=Play Framework — myapp
After=network.target

[Service]
Type=forking
User=play
Group=play
WorkingDirectory=/srv/myapp
PIDFile=/srv/myapp/server.pid
ExecStart=/opt/playframework/play start /srv/myapp --%prod
ExecStop=/opt/playframework/play stop /srv/myapp
Restart=on-failure
RestartSec=5

[Install]
WantedBy=multi-user.target

そして:

bc. systemctl daemon-reload
systemctl enable myapp
systemctl start myapp
journalctl -u myapp -f
